### 2.1 第 1 轮 — 内存安全与越界

> 本轮对 `src/fcp` 核心库给出**重要的负结果**：`frame_rx` / `frame_tx` / `rs` / `cauchy` / `envelope` / `gcm` / `ghash` / `aes` / `gf256` / `stream` / `settle` / `fecstat` / `trace` 未发现可由网络输入触发的越界写或越界读。所有 `std::array`/bitset 下标均有显式护栏（如 `frame_rx.cc:408` 的 `idx >= kMaxS`、`hdr.cc:33` 的 `hdr.index >= s`、`envelope.cc:198` 的 `delta >= recv_seen_.size()`）。

### 2.2 第 2 轮 — 密码学与协议安全

> **正面结论**（该轮明确确认）：GCM 核心实现**正确**。`gcm.cc` 的 J0 构造、`inc32`、GHASH 长度块顺序（AD‖CT‖len(A)‖len(C)）、大端长度编码、12 字节 tag 左截断、tag 先验后解密、常数时间聚合比较，均与 NIST SP 800-38D 一致（`tests/gcm_test.cc` 用 NIST tc1/tc2/tc3 向量）。`gf128_mul` 的 GF(2^128) 约简（`v[0] ^= 0xE1`）也正确。**问题不在原语本身，而在原语周围**：GHASH 的常数时间性、salt 的明文路由与预认证绑定、密钥生命周期、应用层密钥管理。

#### [P2-01] GHASH 乘法按位串行实现，分支模式逐比特泄露 GHASH 认证密钥 H — High

- 位置：`src/fcp/ghash.cc:7-28`
- 涉及代码：
```cpp
void gf128_mul(const uint8_t a[16], const uint8_t b[16], uint8_t out[16]) {
  uint8_t z[16] = {};
  uint8_t v[16];
  std::memcpy(v, b, 16);

  for (int i = 0; i < 128; ++i) {
    if ((a[i >> 3] >> (7 - (i & 7))) & 1) {
      for (int j = 0; j < 16; ++j) {
        z[j] ^= v[j];
      }
    }
    const uint8_t lsb = static_cast<uint8_t>(v[15] & 1);
    for (int j = 15; j > 0; --j) {
      v[j] = static_cast<uint8_t>((v[j] >> 1) | (v[j - 1] << 7));
    }
    v[0] = static_cast<uint8_t>(v[0] >> 1);
    if (lsb != 0) {
      v[0] ^= 0xE1;
    }
  }
  std::memcpy(out, z, 16);
}
```
- 为什么是问题：两个**数据相关分支**。分支 2（`if (lsb != 0)`）的取值序列是 H（= E_K(0)，GCM 认证子密钥）比特移位后的直接函数 —— 128 次分支逐比特泄漏 H；分支 1 泄漏 GHASH 状态（即明文/密文的汉明重量）。每轮一次可预测分支，时序信噪比极高，且各平台一致（GHASH 没有 AES-NI 快路径）。
- 攻击场景：同宿主/同物理核的旁路攻击者测量执行时间或分支轮廓，恢复 H；再用一条已知的 (密文, tag) 对反推 `E_K(J0) = tag ⊕ GHASH(H,A,C)`，即可为任意伪造密文计算合法 tag，**完全伪造报文**（含 HELLO，破坏握手与 FEC 控制面）。
- 严重级别：High　置信度：确认（✓已复核；非恒定时这一事实确定，可利用性需本地时序观测能力）

#### [P2-02] 软件 AES 回退路径使用 T 表，缓存时序可恢复主密钥 — High

- 位置：`src/fcp/aes.cc:66-89`（表构造）、`aes.cc:147-195`（T 表轮函数）
- 涉及代码：
```cpp
struct AesTables {
  uint32_t te0[256]; uint32_t te1[256]; uint32_t te2[256]; uint32_t te3[256]; uint32_t te4[256];
  AesTables() {
    for (int i = 0; i < 256; ++i) {
      const uint8_t s = kSbox[i];
      const uint8_t s2 = xtime(s);
      const uint8_t s3 = static_cast<uint8_t>(s2 ^ s);
      const uint32_t t = (static_cast<uint32_t>(s2) << 24) | (static_cast<uint32_t>(s) << 16) |
                         (static_cast<uint32_t>(s) << 8) | static_cast<uint32_t>(s3);
      te0[i] = t; te1[i] = rotr(t, 8); te2[i] = rotr(t, 16); te3[i] = rotr(t, 24);
      te4[i] = static_cast<uint32_t>(s) * 0x01010101u;
    }
  }
};
```
- 为什么是问题：索引由轮密钥与状态共同决定 → 表项访问的缓存行分布与密钥强相关，是 Bernstein 式经典缓存攻击的教科书目标。`aes128_encrypt_block` 在无 AES-NI 时自动落到该路径，即 **ARM 服务器 / 老旧 x86 / 禁用 AES-NI 的环境**全部受影响。
- 攻击场景：能观测缓存的同机 VM / 共享 L3 攻击者做 cache-timing 采样即可恢复 PSK 派生链上的 AES-128 密钥；`derive_session_key`（`envelope.cc:77-86`）直接以 PSK 为 AES 密钥，一次主密钥恢复即解密所有会话。
- 严重级别：High　置信度：确认

- 为什么是问题：规范 §4.5 明确要求"**每条新分片（未存过的 index）到达触发一次解码**"，即解码是**幂等重试**语义；而这里的 `decoded_once` 是**一次性闩锁**：只要某次解码返回了结构非法的重建，该下标即被永久标记，整个集合的解码路径**永久关闭** —— 哪怕之后又收到新的、能救回该下标的 parity。触发"一次非法重建"并不需要攻击者：`symbol_max` 是"已收符号长度的最大值"，只要集合里先到了一条比发送端 `symbol_max` 短的 data，而在 parity 到达之前 `symbol_max` 还停在较小值上，就可能先解出与真实 `symbol_max` 不一致的结果 → 尾部非零 → 闩锁落下。
- 后果：FEC 冗余被静默放弃（只能靠上层 ARQ 重传），且 `struct_fail` 计数被污染（把一次正常的重建失败记成结构错误）。
- 严重级别：High　置信度：确认（闩锁逻辑确定；触发前提依赖到达时序）

### 2.4 第 4 轮 — 并发与时序竞态

> **该轮的重要结构性结论**：整个代理/引擎栈实际上是**单线程**的 —— `ProxyEngine`、`Session`、`Stream` 均无内部锁，且注释明确写着"One logical thread per session; no internal locks"。唯一的真并发点是 `Reactor` 的 4 个 detached 解析线程，而它的互斥量用法本身是正确的（无锁内回调、无锁序问题）。全库未发现任何 `std::atomic` 参与的数据竞争（唯一的 atomic 是信号标志）。
> 因此本轮的问题几乎全部集中在 **Qt 适配层的容器迭代失效、异步回调的跨轮次失效、以及生命周期/退出顺序**三处，而非锁序或内存序。

### 2.7 第 7 轮 — 数学与算法正确性（GF(2^8) / RS / Cauchy）

## 6. 结论

- 十轮对抗分析共产出 **约 103 条**问题，其中 **2 条 Critical、24 条 High**。
- **最严重的两类问题都不是"复杂逻辑写错了"，而是"判定放在了错误的层级"**：
  - **认证判定放在了认证之前**（[A1]）：salt 明文 + 预认证路由 → 8 字节秒杀会话；AEAD 的威胁模型被整体绕过。
  - **上限判定放在了错误的量上**（[A4]）：ACK 谎报防线比较的是"已分配偏移"而不是"已发出偏移"，导致防线的方向对了、基准错了。
- **第三类问题是"同一事实写了两遍、改了一处"**（[A13][A14][A15] 与 [P10-01]）：这解释了为什么 #29/#30 的自查复查没能发现它们 —— 自查读的是同一份代码的同一个副本。
- **[A11] 是一个"仪器装上了但没接上"的典型**：M4 的浪费重传计数器在生产路径恒为 0，若不先修计数器就去做 WAN 复测，会得到假阴性结论并误关一个候选项。
- 本轮**未在 `src/fcp` 核心库中发现可由网络输入触发的越界写或越界读**（第 1 轮的负结果），核心库的边界护栏总体是自洽的；问题集中在**信任边界的外侧**（Qt 适配层、代理宿主层、CLI/工具层）。

## 8. 第二轮对抗分析（2026-10-31 同日复核，基线 `2276a68` + §7 未提交工作区）

### 8.1 目标与方法差异

第一轮（§2）审的是"代码写得对不对"，本轮刻意换了靶子：**审 §7 那批修复本身**。
同一套 10 轮视角重跑一遍，但每轮先假设 §7 的改动是错的，去找它的反例。结果证明
这个换靶是对的——本轮最重的三条发现全部是 §7 引入或半途而废的：

- **A4 只修了 `cum`，没修 SACK 块**（§7 明确写了"SACK 同规则"，实现却仍拿
  `snd_nxt_` 当上界）。
- **A8 修得过头**：为防止"单个远期 `set_id` 劫持锚点"，改成"丢弃首个远期 set 的
  全部符号"，在稀疏流（丢包率 > 50% 或大窗口跳号）下等于永久黑洞。
- **A9 的 `k` 钳制方向对、时机错**：先到 data 后到 parity 时会把 `n` 锁得比已交付
  的 index 还小，破坏 `delivered <= expected` 这个 settle 层不变量。

同时本轮确认：**§7 的修复没有一条是靠"加一层 if"蒙过去的**，都在对应层做了，
所以本轮新发现主要落在"跨模块口径不一致"和"状态机边界补全"这两类，而非
"防线方向反了"。

#### 一条被证伪的"修复"（记录，避免下一轮重犯）

本轮一度认为"尾丢集合（`release_set` 或容量逐出时仍未结算）应标记 retired，防止迟到
parity 再次结算"，并加了 `TestTailDropIsFinal()`。实际跑出 4 条断言失败，根因是
`settle_test::TestNoReaccountAfterRelease` 明确要求**尾丢集合可被迟到 parity 重建并
结算一次**——这是 FEC 在"最后几包丢失"场景下唯一的修复路径，退休它等于让尾部永久
丢数据。改动已整体回退，`retired` 只赋予 `kAccounted` 集合。
**结论：`kAccounted` 才是"已结算"的唯一判据，`release_set` 不是。**

## 9. R3-1 / R3-23 / R3-24 关闭记录（2026-10-31，v7 密钥编排 + 握手 V4）

§8.7 收尾时唯一未关的 Critical 是 **R3-1（握手无新鲜性）**，R3-23/R3-24 是它的两个附属

### 9.1 为什么必须动线格式

根因不是"窗口太小"也不是"salt 太短"，而是 **`session_key` 的函数定义域里没有新鲜量**：

```text
v6:  session_key = AES128(PSK, salt ‖ 0×8)        # 输入全部来自线上/配置，重放必然复制
```

一条录制的握手重放给新会话，双方得到的 `session_key` 与录制时逐字节相同；而反重放窗口
（§4.1，256 槽）是**每会话新建**的 `highest=0`，历史密文因此整段落回窗口内。窗口类、
salt 加宽类的补丁全部绕不过这一点，所以必须让密钥依赖"本次运行才产生的随机量"。

### 9.2 处置

| ID | 处置 | 结果 |
|---|---|---|
| **R3-1** | `HELLO` 带 16B 客户端 CSPRNG nonce、`HELLO_ACK` 回显 c+s 双 nonce（36/52 字节，magic V3→V4）；`session_key` 改三块定长 CBC-MAC（`AES(PSK,salt‖0⁸)` → `⊕c` → `⊕s`）；双 envelope（握手键永不 rekey、数据键 `configure()` 时 rekey）；ACK 侧 echo 校验把 ACK 绑定到本端挑战 | **已关闭** |
| **R3-23** | 维持 salt 8B（决策），把唯一性责任交给 KDF 的新鲜量：salt 只承担会话查找键，密钥隔离改由双向 nonce 保证 | **已关闭**（换个修法，不加宽） |
| **R3-24** | `kEstablished` 收到**相同** nonce 的 HELLO → 重发 ACK（幂等，覆盖丢包）；**不同** nonce → 计 `hello_refused`、状态不动、不回 ACK | **已关闭** |

### 9.3 关键实现事实（供后续审计复核）

1. **角色由发送方向决定**：`send_direction == kC2S` 的一端是客户端（抽 c_nonce）。
   两端同时发 HELLO 不会分叉——角色不靠"谁先发"。
2. **握手信封存在是必然的**：salt 发现必须在握手成功之前可用，此时数据密钥还不存在，
   只能依赖 `(PSK, salt)`。所以 `hs_env_` 用 `X0`、永不 rekey，且**只**收发 HELLO/ACK；
   `on_wire` 先试 `env_` 再试 `hs_env_`（稳态流量不付第二次尝试的代价）。
3. **握手信封的发送计数器起点必须随机**：重放的 HELLO 会让对端重发 ACK，若起点固定，
   同一 (key, IV) 会封出第二条明文不同的 ACK → GCM 密钥流重用。`hs_env_.set_send_nonce(random_u32())`。
4. **echo 校验是唯一绑定**：客户端必须看到 `ACK.client_nonce == local_nonce_`，服务端必须看到
   `ACK.server_nonce == local_nonce_`。没有它，录制的 ACK 会替客户端"作证"一个它从未发起的挑战。
5. **零 nonce 拒绝**（`kBadNonce`）：`(c,s)=(0,0)` 在 KDF 里也**不等于** v6 键（第二块用 `X0` 掩码），
   但全零挑战本身等于"无挑战"，仍必须显式拒绝并响亮失败。

### 9.5 代价（明确接受）

- **v6 硬断**：两端必须同时升级，无降级协商。`部署运维指南.md` §1.1 给了升级顺序与"误混版本"
  的两种症状（握手失败 `V4 no ACK` / 握手成功但 0 吞吐且 `auth_fail` 上涨）。
- **每会话多 32 字节握手开销**（HELLO 16 → 36、ACK 20 → 52），一次性，不影响稳态 MTU。
- **仍无前向保密**：PSK 泄露 → 该 PSK 下全部历史可解，与 v6 一致。
- **残余**：服务端对重放的 HELLO 仍会建立一个会话（它抽自己的 `s_nonce`，键与录制方不同，
  数据全部 `auth_fail`，2.1s 内或 idle 后回收）。成本与"伪造 HELLO"等价（后者需 PSK），
  由 `max_sessions` + idle 回收承担；要彻底消除需服务端侧挑战-响应去重表，性价比不成立。

### 9.6 同批延后（未变）

R3-25（`try_decode` 每符号全量重构）、R3-26（按 set 结构的内存放大）、R3-27（GHASH 时序侧信道）
状态不变，理由同 §8.4。

### 10.2 关键实现事实（供后续审计复核）

1. **"窗口是不是瓶颈"是唯一的增长许可**：`limited_epoch_` 有两个来源——`pump()` 里有段被
   `min(窗口, rwnd)` 挡住，或 `in_flight_ ≥ send_window_`。两者都还要 `peer_rwnd_seen_`：
   对端首次通告之前，`peer_rwnd_` 是本端配置猜的，拿它当路径证据会让固定窗口测试自己长窗
   （W-15 里 `StaysPutWhenPeerLimited` 最初就是这条漏的）。
2. **估计只当参照，不当上限**：`last_target_ = clamp(2 × acked × rtt / elapsed, min, max)`
   只在**可信 epoch**（`epoch_samples_ ≥ kQueueMinSamples = 8` 条干净 RTT）刷新。一个接近
   停摆的 epoch 估出几十 KB，若拿它当增长上限就回到 W-1 的冻结；若拿它当 `ssthresh` 又不
   设 `max(·, 当前窗口)`，慢启动会被自己的低估计掐死（实测会退化成 +1 段/epoch）。
3. **一个 epoch 不是证据**：排队判断要连续两个 epoch 越过 2× 阈值才减窗，抖动路径四次
   RTT 就能单轮越线；`kQueueMinSamples` 同时管住样本数——窗口小到每 RTT 凑不满 8 段时，
   它也还没有大到值得刹车。
4. **黑洞期间的样本不进 `min_rtt`**：ACK 全断时 RTO 重传按 Karn 规则不产样本，但"断流后
   才回来的 ACK"round trip 里含着整段黑洞，测试必须在恢复 ACK **之前**取窗口快照，否则
   `min_rtt` 被污染，下一轮的判断全错。
5. **回环不能验证自适应**：这个测试管线里 datagram 同 tick 直达、ACK 同 tick 返回，
   `in_flight` 永远顶不满窗口，`limited` 恒假 → 窗口一步不动。W-18 用例给内存管线加了
   可选单向延迟（`Options::wire_latency_ticks`，4 tick = 200ms 往返）才有增长可言。
   同理，早先那轮"回环自适应 2.82 MB/s == 固定 2.82 MB/s"既不证明有效也不证明无效。
6. **§8 护栏未改**：`queued`（`srtt − min_srtt ≥ 40ms`）削 FEC k 是刻意设计，
   `strategy_test` / `session_test` 各有一条用例守着；跨层冲突靠把流级阈值压到它下面解决，
   不是靠改护栏。

### 10.5 复测新增并修的缺陷（第六轮，2026-10-31 深夜 VPS）

五轮的结论里有一条是错的：**"流级丢包 = 拥塞信号"**。WAN 实测把它打穿了——
收尾诊断 `loss_rto=10` 对 `loss_dup≈11000`，即缩窗几乎全部来自 dup-ACK 的第二轮判定，而
在 FEC 后仍有 6% 残留丢失的链路上，"补包的那一个包又被随机丢包吃掉"是常态。逐 epoch ×0.7
让 256 KiB 在不到一秒内落到内置地板 64 KiB，且地板之上再也凑不出"干净且窗口顶满"的 epoch，
于是窗口永久停在地板：单流 1.61 Mbps，同期固定 256 KiB 4.0 Mbps。更糟的是 64 KiB 窗口本身
在这条链路上是病态的（固定 64 KiB 那轮 180 s 只走 12 MB，一次突发加 RTO 指数退避就把隧道饿死）。

处置（W-19）：**丢包项的地板 = 本流的起始窗口**，只有排队（延迟）证据可以把窗口压到它以下；
并把缩窗证据拆开计数（`rto_loss_events` / `dup_loss_events`）打进关闭诊断，让下一次同样的问题
能一眼定位。验证：`stream_test` 36/36（新增 `TestAutoWindowHoldsAtTheStartWindow`，
`TestDupAckCutWaitsForSecondBurst` 改为先把窗口拉到起始值之上再判切窗），Windows Debug/Release
与 VPS Linux Release ctest 各 27/27；复跑 A/B 各两次，自适应 4.34 / 3.64 Mbps 对固定 256 KiB
2.53 / 4.17 Mbps，收尾 `cwnd=262144`（不再塌到地板），四次全部 md5 一致。
接受的残余：**自适应在这条链路上没有收益**（它只是不再有害）；`--window` 因此获得了第二重
含义——它同时是丢包项的地板，把起点设得过大时丢包再也无法把它砍下来，只能靠排队项或人工改参。
并发 4 流同一链路复核（全部 `code=200`、md5 逐一与源站一致）：自适应 3.99 / 3.50 / 3.38 / 3.03
Mbps（聚合 13.90）对固定 256 KiB 3.28 / 3.13 / 3.08 / 2.94 Mbps（聚合 12.43），自适应侧收尾
`rwnd=1048576` 而 `cwnd=262144`——窗口在四流并发下同样没长，因为"本端窗口是在途瓶颈"这条许可
没成立；另有一轮更早的自适应 4 流同向（4.02 / 3.13 / 3.06 / 2.99，聚合 13.20）。差值落在单流
2.53–4.34 Mbps 的抖动之内。

本轮新暴露、**尚未根因**的两条：① 修复前固定 1 MiB 那轮 180 s 只走完 33.19 MB（缺 364 KB），
服务端 `live=0` 而客户端 `live=1`（服务端拆了会话、客户端隧道还留着），同配置复跑一次完整通过；
② 多次 `the peer stopped acknowledging` 其实是**关闭段的最后一条没被 ACK**（`queued == acked`
且数据全部交付，md5 正确），与真正的传输停摆必须在排障时分开读——见 `部署运维指南.md` §10。
另记一条流程侧假故障：Git Bash 的 `kill $CPID` 杀不掉 Windows 侧 exe，两个客户端同时绑 1080
会把连接分到错 PSK 的进程上，症状是 `code=000` 与服务端刷 `unauthenticated first datagram`，
看起来像握手回归但与代码无关（`交付历史.md` §20.3）。
