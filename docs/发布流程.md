# FCP 发布流程

> 面向发版的人：**怎么打一个 tag，然后拿到三件发布物**——
> Linux 服务端 deb（安装）与 Windows/Linux 两个客户端的免安装便携包。
> 包里装了什么看 §3，为什么这么选看 §5，出问题怎么查见 §7。
> 参数与部署细节不在这里重复，见 `部署运维指南.md`。

## 1. 一句话流程

```bash
# 1. 改版本号（唯一真源），提交
echo 0.0.2 > VERSION
git commit -am "release: 0.0.2"

# 2. 打 tag 并推上去 —— 推 tag 就是发版
git tag v0.0.2
git push origin main v0.0.2

# 3. 等 release 工作流跑完，GitHub Releases 页已经有：
#    fcp-proxy_0.0.2_amd64.deb              Ubuntu 服务端（安装）
#    FCP-Client-0.0.2-win64.exe             Windows 客户端（单文件，双击）
#    FCP-Client-0.0.2-x86_64.AppImage       Linux 客户端（双击）
#    SHA256SUMS
```

**tag 必须是 `v` + `VERSION` 文件的内容**，逐字符一致。`prep` job 会把
`v0.0.2` 与 `VERSION` 对比，不一致直接失败——防的是"打了 v0.0.2 的 tag、
包里写着 0.0.1"这种没人会注意的事故。

Linux 侧脚本（本地与 CI 同一份）的输出长这样：

```console
$ scripts/release_build_linux.sh build 0.0.2
== fcp 0.0.2 release build
...
100% tests passed, 0 tests failed out of 30      # 发布门禁
...
== build_deb
== 产出 .../build/packages/fcp-proxy_0.0.2_amd64.deb
```

想先验证整条流水线、又不想发版：在 Actions 页手工触发 `release`，
**不勾 publish**，产物只在 workflow 的 artifacts 里，不创建 Release。

## 2. 流水线结构

`.github/workflows/release.yml`，五个 job：

| job | 平台 | 干什么 | 门禁 |
|---|---|---|---|
| `prep` | ubuntu-latest | 校验 tag 与 `VERSION`，定出版本号/架构/是否发布 | tag 必须匹配 `^v[0-9]+\.[0-9]+\.[0-9]+$`，且等于 `VERSION` |
| `linux-deb` | **ubuntu-22.04** | `scripts/release_build_linux.sh`：configure → build → **ctest** → `scripts/build_deb.py` 打 deb，然后安装冒烟 | ctest 全绿；`dpkg -i` 后 `--version` 正确、§3 的落点都在、conffile 已登记、服务能起监听 45000、卸载干净 |
| `linux-appimage` | **ubuntu-22.04** | aqtinstall 装 Qt → `scripts/release_build_linux_appimage.sh`：build → **ctest** → linuxdeploy → appimagetool → 冒烟 | ctest 全绿；AppDir 里有桌面文件/图标；AppImage 解包启动后活过 6 秒 |
| `windows-client` | windows-latest | aqtinstall 装 Qt → `scripts/release_build_windows.ps1`：build → **ctest** → windeployqt → 部署冒烟 → 7zSD 单文件 exe → 单文件冒烟 | ctest 全绿；部署目录运行时齐备；`--smoke-test` 在部署目录和最终 exe 上都退出 0 |
| `publish` | ubuntu-latest | 收 artifacts、算 `SHA256SUMS`、`gh release create` | 只在 `publish == true` 时跑（push tag，或手工触发且勾了 publish） |

三个构建 job 都是**先测试、后打包**：ctest 红了就没有产物，不存在"测试失败但
deb 已经传上去"的中间态。

本地复现与 CI 用的是**同一份脚本**，所以"本地能过、CI 不过"只可能来自环境
差异，不会来自命令不同：

```bash
# Linux / WSL / 容器（依赖：build-essential cmake ninja-build python3）
scripts/release_build_linux.sh build 0.0.2

# Linux AppImage 客户端（需要 Qt6；aqtinstall 的 QT_ROOT_DIR 或系统 qt6）
scripts/release_build_linux_appimage.sh build 0.0.2

# 只打 deb、不重新编译（产物已经在某处）：Windows 上也能跑，同一条命令
python3 scripts/build_deb.py --bin-dir build/apps/fcp-proxy --version 0.0.2
python3 scripts/build_deb.py --self-test          # 打包器自身的单元自检

# Windows 单文件便携 exe（VS 开发者命令行；Qt 用 aqtinstall 装的目录或 vcpkg 的 qtbase）
pwsh -File scripts/release_build_windows.ps1 -QtRoot "$env:QT_ROOT_DIR" -Version 0.0.2
```

## 3. 包内容与落点

服务端是安装包，两个客户端都是"下载后双击就能跑"的免安装包；
**服务端装完不会自动启动**（理由见 §5 第 2 条）。

**`fcp-proxy_<版本>_amd64.deb`**（Ubuntu 22.04+）

| 路径 | 来源 | 说明 |
|---|---|---|
| `/usr/bin/fcp-proxy-server` | `install(TARGETS … RUNTIME)`（`apps/fcp-proxy/CMakeLists.txt`） | systemd unit 的 `ExecStart` |
| `/usr/bin/fcp-proxy-client` | 同上 | 同网排障用，装服务端的机器上顺手有客户端 |
| `/usr/lib/systemd/system/fcp-proxy.service` | `packaging/debian/fcp-proxy.service` | `EnvironmentFile=-/etc/fcp/fcp-proxy.env`，`ExecStart=/usr/bin/fcp-proxy-server $FCP_ARGS`，`Restart=on-failure` |
| `/etc/fcp/fcp-proxy.env` | `packaging/debian/fcp-proxy.env` | **conffile**（`packaging/debian/conffiles` 显式登记），升级不覆盖 |
| `/usr/share/doc/fcp-proxy/*.md` | `docs/*.md` 全量 + `VERSION` | 文档索引、协议、部署指南都在包里，机器上不联网也能查 |
| `/usr/share/doc/fcp-proxy/copyright` | `packaging/debian/copyright` | ⚠ 仓库还没有 `LICENSE`，见 §8 |

维护者脚本：`postinst`（`daemon-reload` + 打印下一步，不 start）、`prerm`
（remove/purge 时停服务）、`postrm`（purge 时删 `/etc/fcp`、`/var/log/fcp`）。
`/var/log/fcp` 与 `/var/lib/fcp` 由 unit 的 `LogsDirectory=`/`StateDirectory=`
在启动时创建，所以 `--trace=/var/log/fcp/srv` 这种前缀不用手工建目录。

**`FCP-Client-<版本>-win64.exe`**（Windows x64，单文件免安装）

| 内容 | 来源 |
|---|---|
| 自解压外壳 `7zSD.sfx` | `packaging/windows/7zSD.sfx`（LZMA SDK，public domain） |
| 载荷：`fcp_client.exe` + Qt6 运行时（`Qt6Core/Gui/Widgets/Network.dll`、`platforms\qwindows.dll`、styles、MSVC CRT） | `windeployqt` + app-local CRT（`scripts/release_build_windows.ps1`） |

双击这一个 exe 即可运行：7zSD 把载荷解到临时目录后启动 `fcp_client.exe`，
程序退出后清理临时目录；不写 Program Files、不建卸载项、不需要管理员权限。
配置仍由 Qt `QSettings` 写到 `HKCU\Software\FCP\FCPClient`，需要彻底清理时
删除该注册表键。发布说明里给出使用方式；仓库的 `packaging/windows/README.md`
记录了 SFX 模块的来源与配置。

**`FCP-Client-<版本>-x86_64.AppImage`**（Linux x64，免安装）

| 内容 | 来源 |
|---|---|
| `fcp_client` + 完整 Qt6 运行时与平台插件 | `linuxdeploy` + `linuxdeploy-plugin-qt`（`scripts/release_build_linux_appimage.sh`） |
| 桌面文件 / 图标 | `packaging/linux/fcp-client.desktop`、`packaging/linux/fcp-client.svg` |
| `部署运维指南.md` | `docs/` |

AppImage 是单文件：`chmod +x` 后在文件管理器里双击运行。Ubuntu 22.04 若没有
libfuse2，先 `sudo apt install libfuse2`；或设 `APPIMAGE_EXTRACT_AND_RUN=1`
直接解包运行。不安装、不写系统目录；删除文件即卸载。配置写到
`~/.config/FCP/FCPClient.conf`。

## 4. 版本号在哪

| 位置 | 作用 | 谁改 |
|---|---|---|
| `VERSION`（仓库根） | **唯一真源**，`MAJOR.MINOR.PATCH` | 发版的人（随发版一起提交） |
| `CMakeLists.txt` 的 `project(fcp VERSION …)` | 从 `VERSION` 读；CI 用 `-DFCP_RELEASE_VERSION` 覆盖后再校验 | 不改 |
| `src/fcp/version.h` 的 `kProductVersion` | `fcp-proxy-server --version` 的输出，CMake 以 `-DFCP_PRODUCT_VERSION` 注入 | 不改 |
| deb Version / 发布物文件名与版本 / Release 标题 | 全部由上面那一个数字派生 | 不改 |
| `src/fcp/version.h` 的 `kVersionMajor = 6` | **协议版本**（线上 v7 的线格式），与发布版本无关 | 只随协议改版动 |

`VERSION` 是什么语义：`0.0.1`、`0.1.0` 这类语义化版本，配合 `CHANGELOG`-
free 的本仓库习惯——变更内容看 `交付历史.md` 与 git log，不在这里维护第二份
变更列表。`0.x` 期间 API/线格式都还会动，而且 **v7 硬断 v6、不能滚动升级**
（`部署运维指南.md` §1.1），所以 `0.x` 的每次发布都按"两端同时替换"处理。

## 5. 关键决策与理由

1. **Linux 服务端交付 deb，客户端交付 AppImage，两者分开。** 服务端是
   "装一台长期跑的机器"，conffile + systemd unit + 卸载干净这三件事只有包
   管理器给得了；桌面客户端要的是下载后双击运行，不该为了一个 GUI 去装服务端
   包。`fcp-proxy-server --key=…` 手起进程的写法仍然可用（二进制在 `/usr/bin`）。
2. **装完不自动 start。** 默认 `FCP_ARGS` 是空的，没有 PSK 的进程只会退出
   （`--key … is required`）。自动 start 会得到一个"失败—重启—失败"的
   systemd 循环，比不启动更糟。`postinst` 只做 `daemon-reload` 并打印下一步。
3. **参数走 `/etc/fcp/fcp-proxy.env` 的 `FCP_ARGS`，不是逐项环境变量。**
   CLI 的参数集合还在演进（`部署运维指南.md` §5 的窗口四参数就是例子），
   逐项映射等于在包这边再维护一份参数表；`FCP_ARGS` 里放什么，以
   `fcp-proxy-server --help` 为准，包不需要跟着改。唯一的例外是 PSK：
   `FCP_PSK=…` 加 `FCP_ARGS` 里的 `--key-env=FCP_PSK`。unit 用 `DynamicUser`，
   服务用户读不了 root:root 0600 的密钥文件；EnvironmentFile 由 systemd 以
   root 读取后注入进程环境，是包装内唯一不降低文件权限也能用的密钥来源。
4. **在 ubuntu-22.04 上构建。** deb 的 `libc6 >= / libstdc++6 >=` 下限由构建机
   决定。22.04（glibc 2.35、gcc 11）构建出来的包能在 22.04 与 24.04 上装；
   在 24.04 上构建就只能 24.04+。代价是新编译器优化少一点，对 UDP 代理不算事。
5. **deb 用 `scripts/build_deb.py` 自己打（纯 Python 标准库），不用 debhelper，
   也不用 CPack。** deb 就是一个 ar 归档 + 两个 tar.gz，标准库的
   `tarfile`/`gzip` 足够；这样 Windows 与 Linux 上是**同一条命令、同一份代码**
   出包，不依赖 `cpack`/`dpkg-deb`/`fakeroot`/`tar`/`ar`，也不会再遇到
   "CPack 把 description 尾部空白变成第二段落"那类生成器行为差异。
   包内文件的落点仍由 `cmake/FCPPackaging.cmake` 的 `install()` 声明，
   `build_deb.py` 的表与之逐条对齐；`--self-test` 进 ctest，出包后再用
   `dpkg-deb` 复核一遍。
6. **`conffiles` 手写，不赌自动推断。** `/etc` 下的文件是否被 dpkg 当成
   conffile，只取决于 control.tar 里的 `conffiles` 清单；漏了它，运维改过的
   `FCP_ARGS` 会在下一次升级被静默覆盖。所以 `packaging/debian/conffiles`
   显式列出 `/etc/fcp/fcp-proxy.env`，安装冒烟再核一遍 `dpkg-query -W
   -f='${Conffiles}'`——两道都在。
7. **依赖显式写死，不做 shlibdeps 自动推导。** 自动推导在
   `dpkg-shlibdeps` 结论缺失时会退化成"无依赖"；显式清单
   （`libstdc++6 >= 11, libc6 >= 2.35`）配合 ubuntu-22.04 构建机，
   装到缺库的系统上是启动即报缺 `.so`，而不是装完静默什么也没有。
8. **Windows 的 Qt 用 aqtinstall，不用 vcpkg。** vcpkg 源码编 qtbase 在 runner 上
   1–2 小时，容易超时；aqtinstall 拉官方预编译包 3–5 分钟。风险是 Qt 小版本
   与本地 vcpkg 不一致——代码只用 Widgets/Network，且 CI 里有"--smoke-test
   启动并退出 0"的冒烟，真缺东西会当场红。
9. **Windows 客户端交付单文件自解压 exe，不做安装器。** 客户端不写系统目录、
   不注册服务、不需要卸载项；安装器只会多出 SmartScreen/UAC/升级残留与"卸载
   时删配置"的维护面。`windeployqt` 部署目录用 7zSD 打成一个 exe，双击后解到
   临时目录运行，退出即清理；用户看到的就是一个可执行文件，和参考仓库
   `magpie-releases` 的单文件分发方式一致。
10. **7zSD 模块固定随仓库走。** 静默解压模块不依赖发布机预装的第三方工具
    版本，`packaging/windows/7zSD.sfx` 来自 LZMA SDK（public domain），
    打包脚本只负责拼接 `sfx + 配置 + 载荷`；模块缺失时脚本直接失败。
11. **Windows 侧不摆 vcvars。** 脚本不指定 `-G Ninja`，让 CMake 自己挑 Visual
   Studio 生成器（multi-config）：runner 的默认 shell 里没有 `cl.exe`，
   Ninja + 手动导出的环境变量是这类流水线最常见的脆弱点。
12. **Linux 客户端交付 AppImage，服务端不依赖它。** AppImage 把 Qt 运行时与
   插件打进单个文件，双击即运行、删除即卸载；服务端 deb 仍只装服务端与 CLI
   客户端，不需要为了 GUI 多装一套 Qt。AppImage 在 ubuntu-22.04 上构建，
   与 deb 保持同一 glibc 下限。
13. **发布物里不放 `fcp_bench`。** 它是标定工具，输出不稳定，不承诺可用性
    （`部署运维指南.md` §8 的口径）。`fcp_replay` 在 Linux 上随源码走，
    需要时自己编。

## 6. 发版 checklist

- [ ] 工作树干净、`main` 上 ctest 全绿（本机 `build.bat Release` 或
      `ctest --preset windows-x64-release`；Linux 侧跑
      `scripts/release_build_linux.sh` 与
      `scripts/release_build_linux_appimage.sh`）
- [ ] `VERSION` 已改成新版本号并提交
- [ ] `docs/交付历史.md` 追加了本次交付条目（本仓库的变更记录在那里）
- [ ] 若协议/线格式有变：`docs/协议规格.md` 与 `决策记录.md` 已同步，
      且 `部署运维指南.md` §1.1 的兼容表仍然成立
- [ ] `git tag vX.Y.Z && git push origin main vX.Y.Z`
- [ ] Release 页检查：三个产物 + `SHA256SUMS`，说明里的包名与运行方式一致
- [ ] 抽一台 Ubuntu 与一台 Windows 实跑：deb 走 §4 安装；Windows 双击单文件
      exe；Linux 给 AppImage 加可执行位后双击（见 `部署运维指南.md` §4/§5）

## 7. 失败怎么查

| 症状 | 大概率原因 | 处置 |
|---|---|---|
| `prep` 报 "VERSION 文件是 X，tag 是 Y" | 改了 tag 没改 `VERSION`（或反过来） | 删 tag 重打：`git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` |
| `prep` 报 tag 格式 | tag 写成 `0.0.1`（没有 `v`）或 `v0.0.1-beta` | 本项目只接受 `vX.Y.Z`；预发布版本也走三段数字 |
| linux-deb 的 ctest 红 | 代码/环境问题，与打包无关 | 本地 `scripts/release_build_linux.sh` 复现；ctest 的失败详情在 job 日志 |
| 包里出现 `/usr/etc/...` | conffile 落点被改回了 `${CMAKE_INSTALL_FULL_SYSCONFDIR}`（prefix=/usr 时它会算成 `/usr/etc`） | `/etc` 的落点必须是**绝对路径**；`build_deb.py` 的 `ENV_PATH` 与 `cmake/FCPPackaging.cmake` 两处都要保持 `/etc/fcp` |
| `dpkg -i` 报 `missing 'Package' field` | control 里多了一个空行（Description 尾部空白），dpkg 按空行分段 | `build_deb.py` 出包即自检段落数；`python3 scripts/build_deb.py --self-test` 可单独验证 |
| 安装冒烟报 `--version` 不匹配 | 版本注入没生效 | 检查 `-DFCP_RELEASE_VERSION` 与 `FCP_PRODUCT_VERSION` 的传递（`cmake -LA` 看缓存） |
| 安装冒烟报 conffile 未登记 | `/etc/fcp/fcp-proxy.env` 没进 control.tar 的 `conffiles` | 查 `packaging/debian/conffiles` 是否列了它，以及 `build_deb.py` 的 `build_control_tar()` 是否传了它；`dpkg-deb --ctrl-tarfile x.deb \| tar -t` 能看到 |
| 装完 `apt upgrade` 覆盖了运维改的参数 | 同上（conffiles 漏登记） | 同上；这条是"静默失效"，只有安装冒烟会提前发现 |
| 服务起不来（`systemctl is-active` 失败） | `FCP_ARGS` 为空或端口被占 | job 日志里有 `journalctl -u fcp-proxy` 的尾巴；本地用同一份 env 手跑 `fcp-proxy-server $FCP_ARGS` |
| windows 报 `MSB8020`/找不到工具集 | runner 镜像变了 | 重新跑；仍失败就改用 `windows-2022` 固定镜像 |
| windows 报"部署目录缺 Qt6Widgets.dll" | windeployqt 没跑或 Qt 路径错 | 看 `QT_ROOT_DIR` 是否被 `install-qt-action` 设置（`Get-ChildItem env:QT_ROOT_DIR`） |
| exe `--smoke-test` 退出非 0 | 缺 DLL（vc runtime / Qt 插件） | 冒烟步骤会打印退出码；用 `dumpbin /dependents` 对着 `dist\deploy` 查 |
| 部署目录缺 Qt DLL / `platforms\qwindows.dll` | `windeployqt` 没跑或部署目录被上一次残留污染 | 脚本每次从空 `dist\deploy` 开始；检查 `windeployqt` 的退出码与 `-QtRoot` |
| 单文件 exe 双击后没有反应 | 7zSD 载荷没解出来或 `RunProgram` 名字不对 | 用 `7z x FCP-Client-*.exe` 看载荷根目录是否有 `fcp_client.exe`；检查 `packaging/windows/7zSD.sfx` 是否存在 |
| AppImage 报 `qmake`/Qt 路径找不到 | 构建机没有 Qt6 工具链 | CI 用 aqtinstall 的 `QT_ROOT_DIR`；本地设置 `QT_ROOT_DIR` 或装 `qt6-base-dev-tools` |
| AppImage 启动即退出 | Qt 平台插件或 xcb 运行库没打进去 | 看 `linuxdeploy` 日志；CI 已装 xcb 运行库并用 `xvfb-run` 冒烟 |
| `gh release create` 403 | `permissions: contents: write` 被仓库设置覆盖 | 仓库 Settings → Actions → Workflow permissions 改为 "Read and write" |

## 8. 已知限制

- **没有代码签名**：Windows 单文件 exe 下载后仍带 Mark-of-the-Web，SmartScreen
  会弹"未知发布者"；Linux 侧没有 PGP 签名的 Release 文件。要消掉这两条需要
  买证书，不在本期范围。
- **只有 amd64/x86_64**：deb 与 AppImage 都在 `ubuntu-22.04` 上出 amd64；
  arm64 需要加构建矩阵（`ubuntu-22.04-arm` runner）或交叉编译，目前没做。
- **PSK 出现在进程命令行**：`--key=…` 的写法在 `ps` 里可见。多用户主机应改用
  `--key-env=VAR`（deb 的 unit 用 `FCP_PSK` + `--key-env=FCP_PSK`；进程环境
  只有服务用户和 root 可读），或手工前台运行时用 `--key-file=/etc/fcp/psk`
  （内容 32 位十六进制，权限 0600，且须对运行用户可读），见
  `部署运维指南.md` §3。
- **Qt 版本与本地 vcpkg 不保证一致**：CI 用 aqtinstall 的 6.8.3（`release.yml`
  的 `env.QT_VERSION`），本地开发用 vcpkg `qtbase`。两者都满足代码的
  `find_package(Qt6 REQUIRED COMPONENTS Widgets Network)`。
- **`0.x` 的版本号不承诺 ABI/线格式稳定**：见 §4 与 `部署运维指南.md` §1.1。
