# FCP M4 评估：按需项的判定与触发器

> 依据：`协议规格.md` §12.2（M4 行："可选：KCP per-segment 延迟重传、滑动窗口 FEC、
> 大小分桶、非对称 D:P"，验收"按需"）、§9（M1 不改 KCP 行为的定价）、§14.4/§14.7（caps
> 一次性决定）、`M2代理设计.md` §7（M3 修复后的吞吐定价）、`M3控制设计.md`（M3 收口
> 状态）。M4 与 M1–M3 不同：**没有自驱的需求，只有性能优化的候选项**——每项的判定依据必须
> 是实测信号，不是推断。本文档定义四个候选项的机制、成本、现有证据、触发器与判定。

## 0. 当前基线（2026-10-31，M3 收口时）

- 吞吐：LAN 无损 68.9 Mbps（双机联调，#29b）；WAN 180ms/10–17% 丢包上 **8.56 Mbps**
  （#23 探针修复后，**#27 快重/多洞 SACK 之前的数字**——修复后的 WAN 复测是 M4 第一个任务，
  也是所有触发器的数据源）。
- 修复结构：k 在 5%/10%/20% 稳定于 1/2/4 且不顶满 p_max（#28 replay_test）；单块 SACK +
  dup-ACK 快重已消除"等 RTO"节奏（#27，确定性 burst 场景 225ms → 25ms）。
- 待测：快重后 WAN 吞吐、parity 与重传的重复修复量、上下行不对称度、k 轨迹与 KL。

## 1. 候选项判定

### 1.1 FEC-ARQ 协调的延迟重传（对应路线图"KCP per-segment 延迟重传"）

- **机制**：洞出现时 ARQ 立即重传（#27），parity 可能在同一 RTT 内也把它修掉——重传与
  修复赛跑，输的一方是浪费的字节。延迟重传 = 给洞挂一个短定时器（约 0.5–1×RTT），FEC
  先修复则撤销重传。v6 定价的反方向：M1 选择"并存 + 去重"换来简单；现在评估是否值得买回。
- **成本**：流层每洞一个定时器 + 撤销路径；与 dup-ACK 快重（#27）和零窗探测的交互要重新
  审查；撤销时序错了会把"等修复"变成"等两倍"。
- **现有证据**：无直接测量。#22 的 1.19× wire/delivered 中 parity 与重传各占多少不可分；
  间接信号（修好的槽位又收到重传）当时没有计数器。
- **测量仪（已就位，#31）**：接收端 `dup_after_recovered` 计数——槽位被 parity 修复后又
  收到原始副本 = 重传输掉了与 parity 的赛跑 = 纯浪费。已贯通到代理 stats 行（`duprec=N`）。
- **触发器**：WAN 复测中 `duprec / (recovered + rtx segments) ≥ 10%` 且该浪费折算带宽
  ≥ 5%（两者都从统计行与 trace 可算）。低于此阈值不建——定时器复杂度买不回 5%。
- **判定**：**等 WAN 数据**。

### 1.2 滑动窗口 FEC

- **机制**：v5 的滑动窗口编码替代 v6 的固定 D+k 集合——突发长度超过 D 时组级不可修，
  滑窗对长突发天然更韧。
- **成本**：**推翻 v6 的核心简化**——按集合结算（§5.2 是整个 v6 的地基：tail_drop、
  墓碑、k_unknown、账本、FECSTAT 全部挂在集合语义上）；frame/fcp/settle 三层重写。
- **现有证据**：k 在全部测试档位不顶满；KL 突发检测有余量（#26）；GE 坏段（~4.5 符号）
  未超 D=10。
- **触发器**：WAN 复测显示 `k == p_max` 成为常态（p_eff 持续顶格）**且**实测丢包率 > 25%
  （p_max=5..7 也不够的区间），或 GE 坏段长度分布（burst_kl + run_hist）显示 P(游程 > D)
  不可忽略。
- **判定**：**默认不做**。这是四个候选项里唯一推翻地基的；触发器要求的是"协议几何本身
  不够用"，而现有证据是"够用且有余量"。

### 1.3 大小分桶

- **机制**：集合内 parity 的 `symbol_max` 取集合内最大 data 尺寸——混合大小集合里，小段
  也按大段的 parity 尺寸付字节。分桶 = 按尺寸分级组集合，消除该浪费。
- **成本**：FrameTx 分桶破坏输出顺序（乱序延迟）或需要 per-size 集合管理；接收端按集合
  结算不变，但集合的 n 分布变复杂。
- **现有证据**：**无浪费**——v6 的 parity 与 data 每包字节几乎相同（§8.2 勘误的结论），
  冗余比实测 ≈ k/D 理论值（golden 轨迹 0.29@k=3、0.40@k=4，误差来自重传计入 data 字节，
  不是 symbol_max 浪费）。代理 bulk 流量以满尺寸段为主，小段占比低。
- **触发器**：WAN trace 中 `实际冗余比 / (k/D) ≥ 1.15` 持续出现（15% 以上的 parity 字节
  被 symbol_max 撑大）。
- **判定**：**不做**。现有证据显示 v6 的"自然长度 + 集合内最大"已经把浪费消掉了；触发器
  留作 trace 监控项（fcp-replay 可算）。

### 1.4 非对称 D:P

- **机制**：上下行丢包率不对称（ADSL/移动网络常态），当前 D/P 双端对称协商——低丢包方向
  为高丢包方向买单（或反之 k 不足）。
- **成本**：**caps 扩展**——第二组 D/P 字段。§14.7 的红线：caps 是一次性决定，加字段要
  一次做对且永不改宽度。
- **现有证据**：无（从未测过双端各自的 pre_repair_loss 对比）。
- **触发器**：WAN 双端 trace 显示上下行 `pre_repair_loss` 比值持续 ≥ 3×，且高丢包方向的
  k 轨迹被对称协商钳制（k_target > 协商 P'）。
- **判定**：**等 WAN 双端数据**。触发器命中时才设计 caps 扩展（届时连同 §14.4 一起）。

## 3. 已知边界

1. **触发器阈值是初值**：10%/5%/15%/3× 与 §14.1 的门阈值一样，第一次 WAN 复测后校准。
2. `dup_after_recovered` 只在接收端统计（发送端看不到自己的重传输给了谁）；双端各自统计
   自己的入向，WAN 复测时两端 stats 各留一份。
3. 滑动窗口 FEC 的判定刻意设为"默认不做"——若触发器命中，它自成一个里程碑级别的工作
   （v7 量级），不走 M4 的任务列表。
4. M4 关闭的标准：#32 复测后，全部触发器未命中 → M4 就此关闭，路线图 §12.2 的 M4 行
   标注"评估后不做"并留触发器表；命中哪项做哪项。
