## 23. 目录与文件命名收口（2026-11-01）

盘点结论（不跑测试时看仓库前 30 秒能得到什么）：`src/fcp/` 平铺 22 个模块本身是**流水线**，
不该按"crypto/fec/transport"再分裂；不合理的是四处——代理应用层藏在 `apps/fcp-proxy/` 里
被三方共用、跨层复用的模块叫泛名 `engine`、`proxy_proto` 落在协议库里而协议库从不解析代理
报文、三个目录两套源文件后缀。按此整改：

| 项 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 代理应用层落点 | `apps/fcp-proxy/engine.h/.cc` + `src/fcp/proxy_proto.h/.cc`（同一静态库 `fcp_proxy_core` 被拆在两处） | `src/proxy/proxy_engine.h/.cc` + `src/proxy/proxy_proto.h/.cc`，`fcp_proxy_core` 在根 `CMakeLists.txt` 定义 | 一个库的源文件应在同一目录；`libfcp` 回到纯协议；库的位置也不再暗示"属于 CLI 宿主" |
| 跨层模块名 | `engine.h`（`ProxyEngine`） | `proxy_engine.h` | 与 `proxy_proto` 同前缀；`apps/` 里仅有的泛名留给真正私有的 `reactor`。`BenchEngine`（Qt 私有）保持不动 |
| CLI 宿主 | `apps/fcp-proxy/` 在 `FCP_BUILD_TESTS` 时也被 `add_subdirectory` | 只在 `FCP_BUILD_PROXY` 时进入 | 默认门禁里不需要宿主目录；`cli_test` 本来就直编 `cli.cc + reactor.cc` |
| 源文件后缀 | Qt 应用 `.cpp`，其余 `.cc` | 全仓 `.cc` | 一套规则；`moc` 生成物不进仓库，`.cpp` 已无存在理由 |
| 测试产物 | 仓库根出现 `Testing/`、`replay_trace_test/` | 已删，两者进 `.gitignore` | 前者是 ctest 不在 build 目录跑（ctest 未带 `--test-dir`）的残留，后者是 `proxy_engine_test` 落 trace 的相对路径 |

`src/fcp/` 保持平铺的决定写进了 `详细设计.md` §2.0：`frame_rx` 直接调 `rs` 与 `settle` 回调、
`envelope` 是 `frame_*` 唯一出口，按层建目录只会制造互相回指的 `../`，而 22 个文件配
"一模块一文件"的平铺表本身就是最紧的索引。

### 23.1 影响的引用点

- 代码：`src/proxy/*`、`apps/fcp-proxy/{reactor.h,cli.h}`、`apps/fcp-client/proxy_host.{h,cc}`、

  `proxy/proxy_proto.h`（仓库相对路径），不再依赖宿主目录的 `target_include_directories`。
- 构建：根 `CMakeLists.txt`（`libfcp` 去掉 `proxy_proto.cc`、新增 `fcp_proxy_core` 目标）、
  `apps/fcp-proxy/CMakeLists.txt`（只剩宿主三件套）、`apps/fcp-client/CMakeLists.txt`（`.cc`）、
  `tests/CMakeLists.txt`（`proxy_proto_test` 也链 `fcp_proxy_core`）。
- 文档：`M2代理设计.md` §6 模块表、`详细设计.md` §2.0（新增分层表）、两份对抗报告里的行号
  引用路径同步；`M1任务清单.md` §#20/#21 的历史条目按原样保留（记录当时事实，指针到本节）。

## 27. vcpkg manifest 模式接入（2026-11-03，决策 #44）

项目当前零第三方 C++ 依赖，但"依赖从哪里来、版本怎么钉"需要一个确定的答案。
采用 vcpkg **manifest 模式**（方案 A）：`vcpkg.json` 随仓库走，toolchain 由
preset 注入。vcpkg 只负责第三方包，不参与 target 组织——`fcp` /
`fcp_proxy_core` / 两个 CLI / 两个工具 / 29 个测试可执行文件的定义一行未改。

| 项 | 内容 |
|---|---|
| `vcpkg.json` | `dependencies: []`；`builtin-baseline` 固定到 `817892b0ec…`（2026-10-24） |
| `CMakePresets.json` | `windows-x64` 与 `linux-x64` 增加 `toolchainFile: $env{VCPKG_ROOT}/...` |
| `build.bat` | 配置前校验 `VCPKG_ROOT`、`vcpkg.cmake`、`vcpkg.exe`；vcvars 之后恢复用户值（vcvars 会覆盖成 VS 自带 vcpkg） |
| 发布脚本 | `release_build_linux.sh`、`build_linux.sh`、`coverage.sh` 校验 `VCPKG_ROOT` 并显式传 `-DCMAKE_TOOLCHAIN_FILE` |
| CI | 新增 `.github/actions/setup-vcpkg`；三个 C++ job 复用，按 baseline 浅取、bootstrap、缓存 `.vcpkg` |
| 文档 | `部署运维指南.md §1`、`发布流程.md §2`、`apps/desktop/README.md` 补前置与命令 |

使用方式：新增依赖时只在 `vcpkg.json` 的 `dependencies` 加包，再给真正消费它的
target 加 `find_package(... CONFIG REQUIRED)` + `target_link_libraries(<target>
PRIVATE <pkg>::<target>)`；测试链接 `fcp`，按 PUBLIC/PRIVATE 自动继承。版本真源
仍是根 `VERSION`；`vcpkg.json` 的 `version-string` 只是 manifest 元数据。

### 32.3 收端 UDP GRO（P1-4 对偶，2026-11-05）

内核源码定性（`net/ipv4/udp.c` `udp_recvmsg` + `include/linux/udp.h`）：`UDP_GRO`=104
开聚合，收敛后的读经 `recvmsg` 携带 `SOL_UDP/UDP_GRO` cmsg（int 段长）——**拆分尺寸
由内核直接给出，不猜任何 symbol 公式**；仅真聚合的 skb 会有此 cmsg。

- 使能：`setsockopt(SOL_UDP, UDP_GRO, 1)`；内核 6.12 无特权位要求，DynamicUser 可用；
  `ENOPROTOOPT/EPERM` 静默退化普通循环。
- 拆分：`drain_gro()`——cmsg 段长合法且整除才切开，任何异常按单到达处理（FrameRx
  的 `declared == symbol_len` 是兜底校验）。
- 开关：`--no-udp-gro`（默认开）。回环 A/B 实测 GRO 后 down/up 各 −4~5%（回环没有
  NIC 中断聚合的收益、却要付聚合报文的深拷贝），真实网卡路径的收益/损耗随环境而
  变，因此做成运行时开关而不是硬编码。
- Windows/Linux 双侧 32/32；生产 server 已部署带开关版本，`--no-udp-gro`／默认两
  种模式各跑通一轮完整测速。

来源：torvalds/linux `net/ipv4/udp.c`、`include/linux/udp.h`、`include/uapi/linux/udp.h`（v6.12 与 master 语义一致）。

### 32.4 GRO 收侧对抗分析 5 轮（2026-11-05，第二轮）

|---|---|
| 1 收侧缓冲正确性 | **真 bug**：iov 槽步长仍是旧的 64 KiB，而槽容量已被扩为 64×MTU——GRO 束 >64KiB 时槽 i 的溢写会侵入槽 i+1 的区域并被下一槽覆盖（静默污染；普通单报文 ≤64KiB 的测试全测不出）。改为 `udp_slot_bytes_` 统一驱动 iov.base/iov.len 与 arena 分排 |

### 33.2 对抗审计 10 轮（修复 13 处）

三个独立子代理审计 + 本体复查，**修的都是真缺陷**：

| # | 缺陷 | 修法 |
|---|---|---|
| 1 | GSO 批次按 `(peer, 段长)` 分批，peer 槽被 `free_peer` + `peer_retired` 复用后，不同对端数据报合进同一条 `sendmsg` | 批次键加上**地址三元组** `(peer, size, addr)`；`gso_to_` 单独保存 |

| 3 | 看门狗守门在 `tunnels`/`established` 递增计数器（**永不递减**，生命周期总量），活会话死后仍判"还活着" | 门控改 `live != 0` |

| 6 | 每 30s 重复打印 dead 的分支在 `else` 外，永远不会执行 | 移进 else，`still dark` 真 30s 一次 |
| 7 | trace 改名失败（Windows 上目标 .1 存在未 fclose）将 sink 置残废，`written` 停止增长且再无自愈 | 失败回 append 重开，字节保留，下轮重试 |
| 8 | `--rate-limit` 低于每秒一个 MTU 时，整形窗口收不进任何报文——限速**静默成为永远丢帧**（组件不报错地在丢 100%） | 启动即拒，报出"一秒预算装不下一个 MTU，需 ≥ N B/s" |
| 9 | 单报 `len` 超过整秒预算（高位率窗配错、极端 MTU）时整形窗口字节计数变负并毒化后续窗口 | 超预算帧放行且不污染窗口状态 |
| 10 | teardown 强拆会话时整形队列尾还有 hold 的报文没 flush | `flush_wire_deferred(now, /*force=*/true)` 强制排空 |
| 11 | GUI 侧 QString::number(rate,'f',1) 精度损失：0.05 → 0.1（翻倍） | `'g',15` 无损 |
| 12 | 限速回显的小数被截到 3 位，0.0005 Mbps 显示成 0.001、与实际生效值不符 | 保留 6 位小数再裁尾零 |
| 13 | GUI adaptersDigest 把 `OperStatus` 排进身份，网卡 DOWN 半秒就当网络切换重建 | 指纹只留稳定身份字段 |
