## 2. 效力顺序（冲突时以谁为准）

同一件事在多处出现且不一致时，按下面顺序裁定——**越靠上越权威**：

1. **代码**：`apps/fcp-proxy/cli.cc` 的 Usage 文本（参数与默认值的唯一真源）。
2. **`详细设计.md`**：实现行为以它为准；它和规格冲突时，先改规格（规格是契约，
   设计是实现），并在 `决策记录.md` 记一条。
3. **`协议规格.md`**：规范契约。线上字节布局、计数字段语义、不变量以它为准。
4. **`部署运维指南.md` / 各里程碑文档 / `交付历史.md` / 验收记录 / 审查报告**：描述性文档，滞后于以上三者。

发现不一致时不要"就地各改一半"：先确定哪一层是真源，再改其余引用。

## 3. 命名与编号约定

- **文件名用中文、不带协议版本号**（与仓库内其他中文文档一致；代码注释里引用文档用
  中文文件名 + 章节号，如 `协议规格.md §4.1`）。协议版本写在正文（当前线上 v7），
  历史版本差异见 `协议规格.md` 附录 B 与 `决策记录.md`。遗留的线上常量 `FCP_FECSTAT_V6` 是冻结 magic，不改。
- **`#n` 有两种含义，不要混用**：
  - `决策记录.md` 里的 `#n`（`#1`–`#34`）是**决策号**，规格正文里的 `#28①` 一类引用都指向它；
  - 各里程碑文档里的 `#24`–`#39` 是**任务号**，只在该里程碑内有意义。
- **测试编号 `T1`–`T39`** 是规格 §13 测试矩阵的用例号，跨文档通用。
- **章节号 `§n`**：在规格/设计里指该文档自己的章节；引用别的文档时一律带文件名前缀，
  例如 `部署运维指南.md §1.1`、`交付历史.md §16.1`。

## 4. 三条阅读路径

- **部署/运维**：`部署运维指南.md` →（排障时）`部署运维指南.md` §7/§9 →（要懂参数含义时）`协议规格.md` §8。
- **发版**：`发布流程.md` →（包内容/落点）`发布流程.md` §4 →（装与排障）`部署运维指南.md` §4/§5。
- **上手实现/改代码**：`协议规格.md` §2–§8 → `详细设计.md` 对应章节 →
  改了什么先查 `决策记录.md` 有没有历史裁定。
- **审计/复盘**：`对抗分析报告.md`（§7–§10 看处置现状）→ `决策记录.md`（规则演变原因）
  → `M1验收记录.md` 与 `交付历史.md`（证据）。

## 5. 写文档的规矩

- 当前结论写在规格/设计里；**过程**（哪一轮改了什么、为什么）写进 `决策记录.md`，
  不要把修订流水堆在规格头部或验收记录里。
- 验收记录按里程碑定长：收口后冻结，后续事件进 `交付历史.md`，不再往验收记录追加章节。
- 新文档先在本页登记职责与状态；职责有重叠就先合并或改归属，不要新增第二份"某某设计"。
