# FCP 发布流程

> 面向发版的人：**怎么打一个 tag，然后拿到三件发布物**——
> Linux 服务端 deb（安装）与 Windows/Linux 两个客户端的免安装便携包。
> 包里装了什么看 §3，为什么这么选看 §5，出问题怎么查见 §7。
> 参数与部署细节不在这里重复，见 `部署运维指南.md`。

## 1. 一句话流程

```bash
# 1. 改版本号（唯一真源），提交
echo 0.0.1 > VERSION
git commit -am "release: 0.0.1"

# 2. 打 tag 并推上去 —— 推 tag 就是发版
git tag v0.0.1
git push origin main v0.0.1

# 3. 等 release 工作流跑完，GitHub Releases 页已经有：
#    fcp-server-0.0.1-linux-amd64.deb            Ubuntu 服务端（安装）
#    fcp-client-gui-0.0.1-windows-amd64.exe            Windows 客户端（单文件，双击）
#    fcp-client-gui-0.0.1-linux-amd64.AppImage       Linux 客户端（双击）
#    SHA256SUMS
```

**tag 必须是 `v` + `VERSION` 文件的内容**，逐字符一致。`prep` job 会把
tag 去掉 `v` 后与 `VERSION` 对比，不一致直接失败——防的是"改版本号时漏了
其中一处、包名与 tag 对不上"这种没人会注意的事故。

Linux 侧脚本（本地与 CI 同一份）的输出长这样：

```console
$ scripts/release_build_linux.sh build 0.0.1
== fcp 0.0.1 release build
...
100% tests passed, 0 tests failed                 # 发布门禁
...
== build_deb
== 产出 .../build/packages/fcp-server-0.0.1-linux-amd64.deb
```

想先验证整条流水线、又不想发版：在 Actions 页手工触发 `release`，
**不勾 publish**，产物只在 workflow 的 artifacts 里，不创建 Release。

## 2. 流水线结构

`.github/workflows/release.yml`，五个 job：

| job | 平台 | 干什么 | 门禁 |
|---|---|---|---|
| `prep` | ubuntu-latest | 校验 tag 与 `VERSION`，定出版本号/架构/是否发布 | tag 必须匹配 `^v[0-9]+\.[0-9]+\.[0-9]+$`，且等于 `VERSION` |
| `linux-deb` | **ubuntu-22.04** | `scripts/release_build_linux.sh`：configure → build → **ctest** → `scripts/build_deb.sh`（dpkg-deb）打 deb，然后安装冒烟 | ctest 全绿；`dpkg -i` 后 `--version` 正确、§3 的落点都在、conffile 已登记、服务能起监听 45000、卸载干净 |
| `linux-appimage` | **ubuntu-22.04** | `scripts/desktop/build_linux.sh`：建 CLI sidecar → Qt GUI → linuxdeploy（Qt 插件）→ AppImage → 离屏冒烟 | AppImage 启动后存活 6 秒（`timeout` 返回 124） |
| `windows-client` | windows-latest | 建 CLI sidecar → `scripts/desktop/build_windows.ps1`：Qt GUI → windeployqt 收运行库 → 引导器单文件 exe | 引导器 `--fcp-launcher-selftest` 退出 0；缓存里 `Qt6Core.dll`/`platforms/qwindows.dll`/`fcp-client.exe` 齐全；sidecar `--version` 退出 0 |
| `publish` | ubuntu-latest | 收 artifacts、算 `SHA256SUMS`、`gh release create` | 只在 `publish == true` 时跑（push tag，或手工触发且勾了 publish） |

`linux-deb` 是**测试门禁**：ctest 红了就没有任何产物，不存在"测试失败但
deb/客户端已经传上去"的中间态。

三个 C++ job（`linux-deb`、`linux-appimage`、`windows-client`）都先跑仓库内的
composite action `.github/actions/setup-vcpkg`：按 `vcpkg.json` 的
`builtin-baseline` 浅取对应提交、bootstrap，并导出 `VCPKG_ROOT`；缓存键跟随
`vcpkg.json`，改 baseline 或依赖才会重新下载。

本地复现与 CI 用的是**同一份脚本**，所以"本地能过、CI 不过"只可能来自环境
差异，不会来自命令不同：

```bash
# Linux / WSL / 容器（依赖：build-essential cmake ninja-build dpkg
# + 已 bootstrap 的 vcpkg，且已 export VCPKG_ROOT）
scripts/release_build_linux.sh build 0.0.1

# 只打 deb、不重新编译：先按 install() 规则装出一棵 DESTDIR 树，再交给
# dpkg-deb 打包（Linux 上跑；Windows 不能出可安装的 Linux deb）
DESTDIR=/tmp/fcp-stage cmake --install build --strip --prefix /usr
bash scripts/build_deb.sh --stage /tmp/fcp-stage --out-dir build/packages \
  --version 0.0.1 --arch amd64

# 桌面客户端（Qt，见 §2.1）
bash scripts/desktop/build_linux.sh
pwsh -File scripts/desktop/build_windows.ps1 `
  -ProxyBin build\release-win\apps\cli\Release\fcp-client.exe `
  -QtPrefix D:\work\vcpkg\installed\x64-windows
```

### 2.1 Qt 6 客户端

`apps/desktop` 是**唯一的**图形客户端：Qt 6 Widgets 壳，隧道由同一份
`fcp-client` 以 sidecar 子进程承载（密钥走 `FCP_PSK` 环境变量，不进
argv）。两种平台产物都是**免安装、双击运行**：

```bash
# Windows（Qt 6 + MSVC 就绪；先构建 FCP_BUILD_PROXY=ON 的 CLI）
pwsh -File scripts/desktop/build_windows.ps1 `
  -ProxyBin build\release-win\apps\cli\Release\fcp-client.exe `
  -QtPrefix D:\work\vcpkg\installed\x64-windows
# -> dist\fcp-client-gui-<版本>-windows-amd64.exe（单文件引导器；首次运行解到 %LOCALAPPDATA%\FCP\bin）

# Linux / VPS（依赖 qt6-base-dev、patchelf、curl；见 apps/desktop/README.md）
bash scripts/desktop/build_linux.sh
# 想用自编无 ICU 的 Qt（CI 同款）：
bash scripts/desktop/build_qt_noicu.sh ~/qt-noicu-6.8.3
FCP_QT_PREFIX=~/qt-noicu-6.8.3 bash scripts/desktop/build_linux.sh --skip-fcp
# -> dist/fcp-client-gui-<版本>-linux-amd64.AppImage
```

Windows 脚本用 `windeployqt` 收 Qt 运行库，随后按 PE 依赖递归补齐 vcpkg 的
`zlib/zstd/pcre2/double-conversion` 等 Qt 第三方依赖（`windeployqt` 不认识
它们）；MSVC 运行库直接拷 CRT DLL，不打 18 MiB 的 `vc_redist` 安装包。
GUI 只用 Widgets 的 raster 路径，所以 `tls/`、`networkinformation/`、
`imageformats/`、`generic/` 与 `Qt6Network.dll` 在依赖扫描之前就删掉，否则
TUIO 插件会把 Qt6Network/libcrypto/jpeg62 一起带进载荷。载荷是 store-only
zip 再用 LZMA 压缩，最终 exe 约 7.7 MiB（改造前 12.7 MiB）。

Linux 用 linuxdeploy 的 Qt 插件生成 AppImage。CI 自编一份关掉 ICU/OpenSSL/
DBus 的 qtbase（`scripts/desktop/build_qt_noicu.sh`，缓存在 Actions cache），
用 `FCP_QT_PREFIX` 指给 `build_linux.sh`；脚本把 `$FCP_QT_PREFIX/lib` 加进
`LD_LIBRARY_PATH`，否则 linuxdeploy 用 ldd 解析依赖时找不到
`libQt6Widgets.so.6`。不设 `FCP_QT_PREFIX` 时仍可用系统 Qt（`qmake6`）。

两条路径都不产生安装器：Windows 包删除即卸载、不写系统目录；AppImage 是单文件，
`chmod +x` 后双击（无 FUSE 的机器用 `APPIMAGE_EXTRACT_AND_RUN=1`）。旧的
Tauri/WebView 客户端已于 2026-11-04 移除，仓库里不再有第二套 GUI 实现。

注意事项：

- Windows CI 用 `jurplel/install-qt-action` 装官方 Qt（`win64_msvc2022_64`），
  比在 CI 里用 vcpkg 现编 Qt 快得多；`QT_ROOT_DIR` 就是脚本的 `-QtPrefix`。
- `apps/cli/cli.cc` 的网卡枚举必须用 `ifaddrs::ifa_next`（曾写成 `Next`，
  Windows 走了别的分支所以没暴露，Linux 编译直接失败）。

## 3. 包内容与落点

服务端是安装包，两个客户端都是"下载后双击就能跑"的免安装包；
**服务端装完不会自动启动**（理由见 §5 第 2 条）。

**`fcp-server-<版本>-linux-amd64.deb`**（Ubuntu 22.04+）

| 路径 | 来源 | 说明 |
|---|---|---|
| `/usr/bin/fcp-server` | `install(TARGETS … RUNTIME)`（`apps/cli/CMakeLists.txt`） | systemd unit 的 `ExecStart` |
| `/usr/bin/fcp-client` | 同上 | 同网排障用，装服务端的机器上顺手有客户端 |
| `/usr/lib/systemd/system/fcp.service` | `packaging/debian/fcp.service` | `EnvironmentFile=-/etc/fcp/fcp.env`，`ExecStart=/usr/bin/fcp-server $FCP_ARGS`，`Restart=on-failure` |
| `/etc/fcp/fcp.env` | `packaging/debian/fcp.env` | **conffile**（`packaging/debian/conffiles` 显式登记），升级不覆盖 |
| `/usr/share/doc/fcp-server/*.md` | `docs/*.md` 全量 + `VERSION` | 文档索引、协议、部署指南都在包里，机器上不联网也能查 |
| `/usr/share/doc/fcp-server/copyright` | `packaging/debian/copyright` | ⚠ 仓库还没有 `LICENSE`，见 §8 |

维护者脚本：`postinst`（`daemon-reload` + 打印下一步，不 start）、`prerm`
（remove/purge 时停服务）、`postrm`（purge 时删 `/etc/fcp`、`/var/log/fcp`）。
`/var/log/fcp` 与 `/var/lib/fcp` 由 unit 的 `LogsDirectory=`/`StateDirectory=`
在启动时创建，所以 `--trace=/var/log/fcp/srv` 这种前缀不用手工建目录。

**`fcp-client-gui-<版本>-windows-amd64.exe`**（Windows x64，单文件免安装）

| 内容 | 来源 |
|---|---|
| 引导器 `fcp-launcher.exe`（C++/Win32；嵌入图标与版本信息，静态 CRT 零依赖，内置 LZMA 解码器与 zip 读取器） | `apps/desktop/launcher-cpp/` |
| 载荷：`FCP.exe`（Qt 壳）+ Qt6 Core/Gui/Widgets 与平台插件、第三方依赖、MSVC CRT + `fcp-client.exe`（sidecar）+ `version.txt`，打成 store-only zip 后用 LZMA1 压缩 | `scripts/desktop/build_windows.ps1`（windeployqt + 依赖扫描 + `lzma_pack.py`） |
| 80 字节尾部：magic / 版本 / 编解码器 / 偏移 / 压缩与原始长度 / SHA-256 | `scripts/desktop/bundle_windows_portable.ps1` |

双击后首次运行把载荷解到 `%LOCALAPPDATA%\FCP\bin\<SHA-256 前 8 字节>\`，再启动
其中的 `FCP.exe`；之后直接使用缓存，不再解压。换新版本时内容哈希不同，会解到
新目录并自动使用新版；旧版本目录 7 天未启动后清理（正在运行的文件删不掉，
留到下次）。不写 Program Files、不建卸载项、不需要管理员权限。Qt 运行库都在
载荷里，目标机不需要预装 Qt；配置保存在注册表
`HKCU\Software\FCP\FCP Client`（QSettings，勾选“记住设置”时），与版本缓存目录
无关，升级不需要重输。

引导器尾部（小端，80 字节）：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 8 | `FCPBOOT2` |
| 8 | 4 | u32 格式版本（当前为 2） |
| 12 | 4 | u32 编解码器（1 = LZMA1 alone） |
| 16 | 8 | u64 压缩载荷偏移 |
| 24 | 8 | u64 压缩载荷长度 |
| 32 | 8 | u64 解压后长度 |
| 40 | 32 | **压缩载荷**的 SHA-256 |
| 72 | 8 | 保留（0） |

内层 zip 是 store-only，压缩全部交给 LZMA：zip 自带 deflate 收益小且会让
LZMA 失去长距离重复（Qt DLL 之间大量相同页）。拼接脚本用压缩载荷 SHA-256
的前 8 字节（16 个十六进制字符）作为缓存目录名。

排障：

- 自检（解压并确认 `FCP.exe` / `fcp-client.exe` 就位，不启动 GUI）：
  `Start-Process -Wait -FilePath .\fcp-client-gui-<版本>-windows-amd64.exe -ArgumentList "--fcp-launcher-selftest" -PassThru | Select-Object ExitCode`。
  结果同时写到 `%LOCALAPPDATA%\FCP\selftest.txt`。
- 启动失败会弹消息框，并追加到 `%LOCALAPPDATA%\FCP\launcher.log`。
- 手动查看载荷：先用 `tail -c 80` 与 `dd` 按尾部偏移切出 `payload.lzma`，
  去掉 13 字节 LZMA alone 头后解压，再按普通 zip 打开（载荷本身是 store-only zip）。

**`fcp-client-gui-<版本>-linux-amd64.AppImage`**（Linux x64，免安装）

| 内容 | 来源 |
|---|---|
| `FCP`（Qt 壳）+ `fcp-client`（sidecar）+ Qt 6 / xcb 插件及其依赖 | `scripts/desktop/build_linux.sh`（linuxdeploy + Qt 插件） |
| 桌面文件 / 图标 | `apps/desktop/assets/fcp.desktop`、`assets/fcp.png` |

AppImage 是单文件：`chmod +x` 后在文件管理器里双击运行。Ubuntu 22.04 若没有
libfuse2，先 `sudo apt install libfuse2`；或设 `APPIMAGE_EXTRACT_AND_RUN=1`
直接解包运行。不安装、不写系统目录；删除文件即卸载。配置保存在
`~/.config/FCP/FCP Client.conf`（QSettings，勾选“记住设置”时）。

## 4. 版本号在哪

| 位置 | 作用 | 谁改 |
|---|---|---|
| `VERSION`（仓库根） | **唯一真源**，`MAJOR.MINOR.PATCH` | 发版的人（随发版一起提交） |
| `CMakeLists.txt` 的 `project(fcp VERSION …)` | 从 `VERSION` 读；CI 用 `-DFCP_RELEASE_VERSION` 覆盖后再校验 | 不改 |
| `src/fcp/version.h` 的 `kProductVersion` | `fcp-server --version` 的输出，CMake 以 `-DFCP_PRODUCT_VERSION` 注入 | 不改 |
| deb Version / 发布物文件名与版本 / Release 标题 | 全部由上面那一个数字派生 | 不改 |
| `src/fcp/version.h` 的 `kVersionMajor = 1` | **协议版本**（线上 v1 的线格式），与发布版本无关 | 只随协议改版动 |

`VERSION` 是什么语义：`0.0.1`、`0.1.0` 这类语义化版本，配合 `CHANGELOG`-
free 的本仓库习惯——变更内容看 `交付历史.md` 与 git log，不在这里维护第二份
变更列表。`0.x` 期间 API/线格式都还会动，而且 **v7 硬断 v6、不能滚动升级**
（`部署运维指南.md` §1.1），所以 `0.x` 的每次发布都按"两端同时替换"处理。

## 5. 关键决策与理由

1. **Linux 服务端交付 deb，客户端交付 AppImage，两者分开。** 服务端是
   "装一台长期跑的机器"，conffile + systemd unit + 卸载干净这三件事只有包
   管理器给得了；桌面客户端要的是下载后双击运行，不该为了一个 GUI 去装服务端
   包。`fcp-server --key=…` 手起进程的写法仍然可用（二进制在 `/usr/bin`）。
2. **装完不自动 start。** 默认 `FCP_ARGS` 是空的，没有 PSK 的进程只会退出
   （`--key … is required`）。自动 start 会得到一个"失败—重启—失败"的
   systemd 循环，比不启动更糟。`postinst` 只做 `daemon-reload` 并打印下一步。
3. **参数走 `/etc/fcp/fcp.env` 的 `FCP_ARGS`，不是逐项环境变量。**
   CLI 的参数集合还在演进（`部署运维指南.md` §5 的窗口四参数就是例子），
   逐项映射等于在包这边再维护一份参数表；`FCP_ARGS` 里放什么，以
   `fcp-server --help` 为准，包不需要跟着改。唯一的例外是 PSK：conffile 写
   `FCP_PSK=…` 一行就够了——CLI 在未给 `--key*` 参数时默认读该环境变量（显式
   `--key-env=FCP_PSK` 依旧等价）。unit 用 `DynamicUser`，服务用户读不了
   root:root 0600 的密钥文件；EnvironmentFile 由 systemd 以 root 读取后注入
   进程环境，是包装内唯一不降低文件权限也能用的密钥来源。
4. **在 ubuntu-22.04 上构建。** deb 的 `libc6 >= / libstdc++6 >=` 下限由构建机
   决定。22.04（glibc 2.35、gcc 11）构建出来的包能在 22.04 与 24.04 上装；
   在 24.04 上构建就只能 24.04+。代价是新编译器优化少一点，对 UDP 代理不算事。
5. **deb 用 `scripts/build_deb.sh` 调 `dpkg-deb` 打，不用 debhelper / CPack /
   Python。** deb 只在 Linux 构建机上产出，`dpkg-deb` 本来就是 dpkg 自带、且
   安装冒烟也要用它；再维护一套 ar/tar 写入器（含单元自检）纯属重复实现。
   现在的分工是：`packaging/FCPPackaging.cmake` 的 `install()` 是**唯一**落点真源，
   `cmake --install` 装出一棵 DESTDIR 树，`build_deb.sh` 只往这棵树里补
   `DEBIAN/`（control、conffiles、维护者脚本）再交给 `dpkg-deb --build`。
   因此不存在"打包器的文件表与 install() 漂移"，也没有 CPack 那类生成器行为差异。
   脚本出包后会用 `dpkg-deb` 回读校验字段、conffiles 与落点。
6. **`conffiles` 手写，不赌自动推断。** `/etc` 下的文件是否被 dpkg 当成
   conffile，只取决于 control.tar 里的 `conffiles` 清单；漏了它，运维改过的
   `FCP_ARGS` 会在下一次升级被静默覆盖。所以 `packaging/debian/conffiles`
   显式列出 `/etc/fcp/fcp.env`，安装冒烟再核一遍 `dpkg-query -W
   -f='${Conffiles}'`——两道都在。
7. **依赖显式写死，不做 shlibdeps 自动推导。** 自动推导在
   `dpkg-shlibdeps` 结论缺失时会退化成"无依赖"；显式清单
   （`libstdc++6 >= 11, libc6 >= 2.35`）配合 ubuntu-22.04 构建机，
   装到缺库的系统上是启动即报缺 `.so`，而不是装完静默什么也没有。
8. **客户端用 Qt 6 Widgets，不用 WebView（2026-11-04 起）。** 旧版 Tauri 2 的
   Linux AppImage 必须把 WebKitGTK/JSC/ICU 整套打进去（77 MiB，解压后约
   259 MiB），Windows 又依赖系统 WebView2、版本不受仓库控制。Qt Widgets 是
   纯 C++ 链接，AppImage 只带 Qt 运行库与 xcb 插件，体积和启动时间都小一个
   量级；隧道仍由现成的 `fcp-client` 以 sidecar 承载，传输面零改动，CLI 的
   `--log`/`--trace` 排障手段可直接复用。
9. **Windows 客户端交付单文件引导器 exe，不做安装器。** 客户端不写系统目录、
   不注册服务、不需要卸载项；安装器只会多出 SmartScreen/UAC/升级残留与"卸载
   时删配置"的维护面。Qt GUI 构建目录 + 一个很小的 C++/Win32 引导器打成一个 exe（cmake 独立工程，
   无第三方运行时）：
   首次双击解到 `%LOCALAPPDATA%\FCP\bin` 缓存，之后直接启动，避免每次运行都
   解压；用户看到的就是一个可执行文件。
10. **引导器随源码构建，缓存按载荷哈希分目录。** 不再依赖发布机预装的 7-Zip
    自解压模块：`apps/desktop/launcher-cpp` 现编 cmake，内置 LZMA1 解码器与
    miniz，`bundle_windows_portable.ps1` 只负责拼接 `引导器 + LZMA 载荷 + 尾部`。
    缓存目录名取压缩载荷 SHA-256 的前 8 字节，换版本自然落到新目录；旧目录
    7 天未使用后清理。用户配置在 QSettings（注册表
    `HKCU\Software\FCP\FCP Client`），与缓存目录分离，升级不需要重输。
11. **Windows 侧不摆 vcvars。** CLI 的 CMake 构建不指定 `-G Ninja`，让 CMake
   自己挑 Visual Studio 生成器（multi-config）：runner 的默认 shell 里没有
   `cl.exe`，Ninja + 手动导出的环境变量是这类流水线最常见的脆弱点。Qt 用
   `jurplel/install-qt-action` 的官方二进制。
12. **Linux 客户端交付 AppImage，服务端不依赖它。** AppImage 把 Qt 运行库、
   xcb 平台插件与 sidecar 打进单个文件，双击即运行、删除即卸载；服务端 deb
   仍只装服务端与 CLI 客户端，不需要为了 GUI 多装一套桌面运行时。AppImage
   在 ubuntu-22.04 上构建，与 deb 保持同一 glibc 下限。CI 自编 qtbase 并关掉
   ICU/OpenSSL/DBus：发行版 Qt6Core 依赖的 ICU 数据在 AppImage 里占 ~35 MiB
   （解包后），而界面只用 UTF-8 与 Widgets，不需要 ICU 的本地化排序/转码。
13. **发布物里不放 `fcp-bench`。** 它是标定工具，输出不稳定，不承诺可用性
    （`部署运维指南.md` §8 的口径）。`fcp-replay` 在 Linux 上随源码走，
    需要时自己编。

## 7. 失败怎么查

| 症状 | 大概率原因 | 处置 |
|---|---|---|
| `prep` 报 "VERSION 文件是 X，tag 是 Y" | 改了 tag 没改 `VERSION`（或反过来） | 删 tag 重打：`git tag -d vX.Y.Z && git push --delete origin vX.Y.Z` |
| `prep` 报 tag 格式 | tag 写成 `0.0.1`（没有 `v`）或 `v0.0.1-beta` | 本项目只接受 `vX.Y.Z`；预发布版本也走三段数字 |
| linux-deb 的 ctest 红 | 代码/环境问题，与打包无关 | 本地 `scripts/release_build_linux.sh` 复现；ctest 的失败详情在 job 日志 |
| 包里出现 `/usr/etc/...` | conffile 落点被改回了 `${CMAKE_INSTALL_FULL_SYSCONFDIR}`（prefix=/usr 时它会算成 `/usr/etc`） | `/etc` 的落点必须是**绝对路径**；`packaging/FCPPackaging.cmake` 里保持 `/etc/fcp` |
| `dpkg -i` 报 `missing 'Package' field` | control 里多了一个空行（Description 尾部空白），dpkg 按空行分段 | `scripts/build_deb.sh` 出包即自检段落数；`bash -n scripts/build_deb.sh` 可先查语法 |
| 安装冒烟报 `--version` 不匹配 | 版本注入没生效 | 检查 `-DFCP_RELEASE_VERSION` 与 `FCP_PRODUCT_VERSION` 的传递（`cmake -LA` 看缓存） |
| 安装冒烟报 conffile 未登记 | `/etc/fcp/fcp.env` 没进 control.tar 的 `conffiles` | 查 `packaging/debian/conffiles` 是否列了它，以及 `build_deb.sh` 有没有把它拷进 `DEBIAN/`；`dpkg-deb --ctrl-tarfile x.deb \| tar -t` 能看到 |
| 装完 `apt upgrade` 覆盖了运维改的参数 | 同上（conffiles 漏登记） | 同上；这条是"静默失效"，只有安装冒烟会提前发现 |
| 服务起不来（`systemctl is-active` 失败） | `FCP_ARGS` 为空或端口被占 | job 日志里有 `journalctl -u fcp` 的尾巴；本地用同一份 env 手跑 `fcp-server $FCP_ARGS` |
| windows 报 `MSB8020`/找不到工具集 | runner 镜像变了 | 重新跑；仍失败就改用 `windows-2022` 固定镜像 |
| windows 报"找不到 link.exe"或 GUI build 失败 | 没装 MSVC 生成工具，或 Qt 的 arch 与编译器不匹配 | runner 用 `install-qt-action` 的 `win64_msvc2022_64`；本地装 VS "使用 C++ 的桌面开发" 后重开终端 |
| sidecar `--version` 退出非 0 | `fcp-client.exe` 没构建或路径不对 | 先用 `-DFCP_BUILD_PROXY=ON` 构建，再检查 `-ProxyBin` 指向的文件是否存在 |
| 报"cmake（引导器）失败" | 构建机没有 MSVC / CMake，或 launcher-cpp 编译失败 | 确认 `cmake --version` 与 VS "使用 C++ 的桌面开发"；单独 `cmake -S apps/desktop/launcher-cpp -B build/launcher -DAPP_VERSION=0.0.4 && cmake --build build/launcher --config Release` 看详细错误 |
| 单文件 exe 双击后弹"找不到 Qt6Core.dll / libpng16.dll" | 载荷缺 Qt 运行库或 vcpkg 的第三方依赖 | 看 `build\gui-stage` 是否完整；脚本的 dumpbin 依赖扫描没跑起来（找不到 dumpbin）时会漏 `zlib/zstd/pcre2/libpng` 等，装 VS 的 C++ 工具链后重跑 |
| 单文件 exe 双击后没有反应 | 引导器自检失败或载荷损坏 | 跑 `--fcp-launcher-selftest` 看退出码；失败详情在 `%LOCALAPPDATA%\FCP\launcher.log`；按 §3 的尾部格式切出 `payload.lzma` 解压后确认 zip 根目录有 `FCP.exe`、`fcp-client.exe`、`platforms/qwindows.dll` |
| 换新版本后配置没了 | 改了 QSettings 的 organization/application 名 | `src/main.cpp` 保持 `FCP` / `FCP Client` 不变（注册表 `HKCU\Software\FCP\FCP Client`） |
| Linux 构建报找不到 Qt6 | 没装 Qt 6 Widgets 开发包，或 `CMAKE_PREFIX_PATH` 不对 | `sudo apt install qt6-base-dev`；或给 `apps/desktop` 单独 configure 时传 `-DCMAKE_PREFIX_PATH=<Qt6 前缀>` |
| linuxdeploy 报找不到 qmake | Qt 6 的 qmake 叫 `qmake6`，插件没认出来 | 确认 `qmake6` 在 PATH，或 `QMAKE=/usr/lib/qt6/bin/qmake bash scripts/desktop/build_linux.sh`；自编 Qt 用 `FCP_QT_PREFIX`，脚本会自动选它的 `bin/qmake` |
| linuxdeploy 报 `Could not find dependency: libQt6Widgets.so.6` | 自编 Qt 不在系统库路径，ldd 解析不到 | `build_linux.sh` 已把 `$FCP_QT_PREFIX/lib` 加进 `LD_LIBRARY_PATH`；手工跑时也要设同一个变量（`FCP_QT_PREFIX` 本身不够） |
| AppImage 启动即退出 | Qt 运行库或 xcb 插件没打进去 | 看 linuxdeploy 的 Qt 插件日志；CI 已用 `xvfb-run` 做离屏冒烟，缺 `libxcb-cursor0` 时先装上再冒烟 |
| `gh release create` 403 | `permissions: contents: write` 被仓库设置覆盖 | 仓库 Settings → Actions → Workflow permissions 改为 "Read and write" |

## 8. 已知限制

- **没有代码签名**：Windows 单文件 exe 下载后仍带 Mark-of-the-Web，SmartScreen
  会弹"未知发布者"；Linux 侧没有 PGP 签名的 Release 文件。要消掉这两条需要
  买证书，不在本期范围。
- **只有 amd64/x86_64**：deb 与 AppImage 都在 `ubuntu-22.04` 上出 amd64；
  arm64 需要加构建矩阵（`ubuntu-22.04-arm` runner）或交叉编译，目前没做。
- **PSK 出现在进程命令行**：`--key=…` 的写法在 `ps` 里可见。多用户主机应改用
  `--key-env=VAR`（deb 的 unit 只在 `/etc/fcp/fcp.env` 写 `FCP_PSK=…` 一行，
  CLI 无 `--key*` 参数时默认读它；进程环境
  只有服务用户和 root 可读），或手工前台运行时用 `--key-file=/etc/fcp/psk`
  （内容 32 位十六进制，权限 0600，且须对运行用户可读），见
  `部署运维指南.md` §3。
- **Qt 运行库随发布物走**：Windows 载荷与 Linux AppImage 都自带 Qt 6，目标机
  不需要预装；版本由构建机（vcpkg / install-qt-action / qt6-base-dev）锁定，
  升级 Qt 需要重新发版。
- **`0.x` 的版本号不承诺 ABI/线格式稳定**：见 §4 与 `部署运维指南.md` §1.1。
