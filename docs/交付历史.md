## 22. CLI 参数解析补测（2026-11-01，盘点补盲的第二批）

用户问"还有什么模块测试可以补充"。把 `src/fcp` 的 21 个模块与 26 个测试文件逐一对照后
确认**核心库已无未测模块**（此前的疑点核实为已覆盖：`kfor` 是 `strategy.h` 函数、
`trace` 由 `replay_test` 覆盖 encode->decode->replay 决定性与坏行拒绝）。唯一真正的空白是
**`apps/fcp-proxy/cli.cc`（399 行，零测试）**——且它不在 `fcp_proxy_core` 里，默认门禁
（`FCP_BUILD_TESTS`，`FCP_BUILD_PROXY=OFF`）连编译都没碰过它的逻辑。

### 22.1 重构：解析提炼为纯函数

- `cli.h` 新增 `struct ProxyArgs { EngineConfig ec; ReactorOptions ro; bool help;
  std::vector<std::string> notes; }` 与
  `bool parse_proxy_args(EngineRole, int argc, char** argv, ProxyArgs*, std::string* error)`。
  纯解析：无 I/O、无引擎构造、无进程退出；`--help` 走 `out->help` 不算错误；
  autotune 的两条 stderr 提示改为数据进 `notes`（run_proxy 代为打印，测试可断言）。
- `run_proxy` 缩为编排：parse -> 失败打 error + usage -> help 打 usage -> 打 notes ->
  构造 Reactor。每个范围检查的错误文案逐字保留（原 fprintf -> error 字符串）。

## 23. 目录与文件命名收口（2026-11-01）

盘点结论（不跑测试时看仓库前 30 秒能得到什么）：`src/fcp/` 平铺 22 个模块本身是**流水线**，
不该按"crypto/fec/transport"再分裂；不合理的是四处——代理应用层藏在 `apps/fcp-proxy/` 里
被三方共用、跨层复用的模块叫泛名 `engine`、`proxy_proto` 落在协议库里而协议库从不解析代理
报文、三个目录两套源文件后缀。按此整改：

| 项 | 改前 | 改后 | 理由 |
|---|---|---|---|
| 代理应用层落点 | `apps/fcp-proxy/engine.h/.cc` + `src/fcp/proxy_proto.h/.cc`（同一静态库 `fcp_proxy_core` 被拆在两处） | `src/proxy/proxy_engine.h/.cc` + `src/proxy/proxy_proto.h/.cc`，`fcp_proxy_core` 在根 `CMakeLists.txt` 定义 | 一个库的源文件应在同一目录；`libfcp` 回到纯协议；库的位置也不再暗示"属于 CLI 宿主" |
| 跨层模块名 | `engine.h`（`ProxyEngine`） | `proxy_engine.h` | 与 `proxy_proto` 同前缀；`apps/` 里仅有的泛名留给真正私有的 `reactor`。`BenchEngine`（Qt 私有）保持不动 |
| CLI 宿主 | `apps/fcp-proxy/` 在 `FCP_BUILD_TESTS` 时也被 `add_subdirectory` | 只在 `FCP_BUILD_PROXY` 时进入 | 默认门禁里不需要宿主目录；`cli_test` 本来就直编 `cli.cc + reactor.cc` |
| 源文件后缀 | Qt 应用 `.cpp`，其余 `.cc` | 全仓 `.cc` | 一套规则；`moc` 生成物不进仓库，`.cpp` 已无存在理由 |
| 测试产物 | 仓库根出现 `Testing/`、`replay_trace_test/` | 已删，两者进 `.gitignore` | 前者是 ctest 不在 build 目录跑（ctest 未带 `--test-dir`）的残留，后者是 `proxy_engine_test` 落 trace 的相对路径 |

`src/fcp/` 保持平铺的决定写进了 `详细设计.md` §2.0：`frame_rx` 直接调 `rs` 与 `settle` 回调、
`envelope` 是 `frame_*` 唯一出口，按层建目录只会制造互相回指的 `../`，而 22 个文件配
"一模块一文件"的平铺表本身就是最紧的索引。

### 23.1 影响的引用点

- 代码：`src/proxy/*`、`apps/fcp-proxy/{reactor.h,cli.h}`、`apps/fcp-client/proxy_host.{h,cc}`、
  `tests/proxy_{engine,proto}_test.cc` 的 `#include` 一律改为 `proxy/proxy_engine.h` /
  `proxy/proxy_proto.h`（仓库相对路径），不再依赖宿主目录的 `target_include_directories`。
- 构建：根 `CMakeLists.txt`（`libfcp` 去掉 `proxy_proto.cc`、新增 `fcp_proxy_core` 目标）、
  `apps/fcp-proxy/CMakeLists.txt`（只剩宿主三件套）、`apps/fcp-client/CMakeLists.txt`（`.cc`）、
  `tests/CMakeLists.txt`（`proxy_proto_test` 也链 `fcp_proxy_core`）。
- 文档：`M2代理设计.md` §6 模块表、`详细设计.md` §2.0（新增分层表）、两份对抗报告里的行号
  引用路径同步；`M1任务清单.md` §#20/#21 的历史条目按原样保留（记录当时事实，指针到本节）。

### 23.2 验证

|---|---|

## 24. 去重收口：字序、KCP 偏移、引擎双端构造（2026-11-01）

盘点"哪些模块能缩"的结论：**加密与线格式模块不动**（单次使用的小函数删了省不了几行，却少一层
与 golden 对照的路径），真正该改的是"同一事实写多遍"的三处（决策 #35）：

| 事实 | 改前 | 改后 |
|---|---|---|
| LE/BE 整数读写 | `stream.cc get_u32/put_u32`、`fecstat.cc write16/32 read16/32`、`hdr.cc` 内联移位链、`envelope.cc store_le64/load_le64`、`proxy_proto.cc` 内联 BE16 + 4 处 `"FCPO"` | `src/fcp/wire.h`（全 `constexpr`，`kOpenMagic` 常量） |
| KCP sn 在偏移 12 | `session.cc kcp_sn_of`、`bench_engine.cc`×2、`e2e_link.h`、`session_test.cc` 各写一遍 | 全部调 `kcp_sn_of`；偏移只由 `session.h kKcpSnOffset/kKcpSnLen` 定义 |
| 两端共有的 `SessionConfig` 字段 + 三个宿主回调 | `proxy_engine.cc` 的 `create_client_conn` / `create_server_conn` 逐字段各抄一遍（A15/B11） | `fill_session_config()` + `make_session()`，两端只剩 salt/方向/`phase` |

另：`trace.cc` 四个整数字段 lambda 收敛为 `int_field`；`cli.cc` 补 `#include "fcp/version.h"`
（`--version` 的符号此前靠传递包含，`cli_test` 直编时才暴露）。

### 24.1 验证

| 门禁 | 结果 |
|---|---|
| `ctest -C Debug` / `-C Release` | 各 **30/30**（新增 `wire_test`：字面字节断言 + `constexpr` `static_assert` + FEC 头 golden） |
| `windows-x64-app` `--target fcp_client` | 通过（`bench_engine` 改调 `fcp::kcp_sn_of`） |
| `FCP_BUILD_PROXY=ON` | 两 CLI 构建通过；`fcp-proxy-client --version` → `0.0.1` |
