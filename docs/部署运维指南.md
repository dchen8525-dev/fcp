## 1. 构建矩阵

所有 CMake 构建都走 **vcpkg manifest 模式**：根目录 `vcpkg.json` 只声明第三方
依赖（当前 `dependencies: []`），`CMakePresets.json` 通过 `$env{VCPKG_ROOT}`
加载 toolchain。首次构建前先准备 vcpkg（Linux/macOS）：

```bash
git clone https://github.com/microsoft/vcpkg.git ~/vcpkg
~/vcpkg/bootstrap-vcpkg.sh -disableMetrics
export VCPKG_ROOT=~/vcpkg          # 写进 shell profile 或 CI 环境
```

Windows：

```bat
git clone https://github.com/microsoft/vcpkg.git D:\vcpkg
D:\vcpkg\bootstrap-vcpkg.bat
setx VCPKG_ROOT D:\vcpkg
```

`vcpkg.json` 的 `builtin-baseline` 固定 ports 树版本，保证各机器解析到同一批
包；升级 vcpkg 时改这一处并在 PR 里说明。下表中手工 `cmake ...` 命令都要补
`-DCMAKE_TOOLCHAIN_FILE="$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake"`；
`build.bat`、`release_build_linux.sh`、`build_linux.sh`、`coverage.sh` 已自动传入。

| 产物 | 平台 | 命令 |
|---|---|---|
| 代理 CLI（client/server） | Windows | `cmake -B build/proxy -S . -DCMAKE_BUILD_TYPE=Release -DFCP_BUILD_PROXY=ON` + `cmake --build build/proxy --config Release` |
| 代理 CLI | Linux | `cmake -B build/rel -S . -DCMAKE_BUILD_TYPE=Release -DFCP_BUILD_PROXY=ON && cmake --build build/rel -j$(nproc)` |
| 桌面客户端 | Windows | 先建 sidecar：`cmake -B build/release-win -DFCP_BUILD_PROXY=ON` + `cmake --build build/release-win --config Release`；再 `pwsh -File apps/desktop/scripts/build_windows.ps1 -ProxyBin build\release-win\apps\cli\Release\fcp-client.exe`（需要 Rust/Node/7-Zip） |
| 桌面客户端 | Linux | `bash apps/desktop/scripts/build_linux.sh`（需要 Rust/Node 与 webkit2gtk-4.1 开发包；脚本自己构建 sidecar） |
| 工具（fcp-bench / fcp-replay） | 双端 | 默认随 `FCP_BUILD_TOOLS=ON` 构建，无需额外开关 |
| 全部单测（31 项） | 双端 | `build.bat [Debug\|Release]`（Windows）/ `ctest --preset linux-x64-debug`（Linux） |

- 门禁标准：**Windows × Debug/Release + Linux × Debug/Release 四套 ctest 31/31**。
- Linux 没有 release 构建预设：手动 `-DCMAKE_BUILD_TYPE=Release` 配第二棵构建树。
- 桌面客户端（`apps/desktop`）是 Tauri 2 壳 + WebView，隧道由 `fcp-client`
  以 sidecar 子进程承载；壳本身不链接 `fcp_proxy_core`。

### 1.1 版本兼容（v7 硬断 v6，R3-1）

**v7 与 v6 不能互通，升级必须两端同时替换。** 这不是"协商降级"，两端各自拒绝对方：

| 层 | v6 | v7 | 表现 |
|---|---|---|---|
| 握手 magic | `FCP_HELLO_V3` | `FCP_HELLO_V4` | magic 兼作握手版本号；旧 magic 一律不识别 → 3 次重试后 `V4 no ACK after 3 tries` |
| HELLO 长度 | 20 | 36（多 16B 发送方 nonce） | 长度门限不符，直接丢弃 |
| HELLO_ACK 长度 | 20 | 52（回显 c_nonce + s_nonce） | 同上 |
| 会话密钥 | `AES_psk(salt‖0^8)` | `AES_psk(AES_psk(AES_psk(salt‖0^8) ⊕ c_nonce) ⊕ s_nonce)` | 密钥不同 → 数据面全丢（`auth_fail` 陡增） |
| 数据密文 | 同一把密钥 | 与握手密钥分离（双 envelope） | 旧版本用握手密钥解数据 → 全丢 |

升级步骤（**不能滚动升级**）：
1. 窗口期停服务端 → 换 `fcp-server` → 换全部 `fcp-client`（桌面客户端内置的 sidecar 也要换成同版本）→ 起服务端。
2. 若误混版本，症状是**握手失败**（日志 `V4 no ACK`）或**握手成功但 0 吞吐**（`auth_fail` 持续增长）。
   握手成功但吞吐为 0 时若还能看到 `struct_fail` 一起涨，说明对端仍停在握手 epoch：它的数据包用
   握手键封出、能过认证但不是 HELLO/ACK，被 `struct_fail` 记账（F-2 之前这种情况两个计数都不动，
   只剩"对端没数据"）。这些都不是网络/防火墙问题，先核对版本。
3. `fcp-bench` 的会合格式未变（salt 交换仍在会合包里），但两端都必须是 v7 才有意义。
4. PSK 与 salt 宽度未变（16B / 8B）：**不需要改任何配网或密钥材料**。


## 2. 二进制与角色

| 文件 | 角色 |
|---|---|
| `fcp-server` | 服务端：监听一个 UDP 端口，按 SOKS5/HTTP-CONNECT 语义代理客户端拨号 |
| `fcp-client` | 客户端：本地 SOCKS5(:1080)/HTTP(:1080 同端口自适应) 入口，流量经 FCP 到服务端 |
| `FCP.exe` | Tauri GUI：表单 + 状态 + 日志；隧道由同目录的 `fcp-client` sidecar 承载 |
| `fcp-bench` | 无交付义务的吞吐标定（对照"天花板"用） |
| `fcp-replay` | 控制器轨迹回放（`--trace` 录制文件的离线分析） |

## 3. 密钥与端口规划

- **PSK**：16 字节，两端一致；三种来源任选其一：
  `--key=HEX32`（32 位十六进制）、`--key-file=FILE`（文件里就是 32 位十六进制，
  允许首尾空白）或 `--key-env=VAR`（环境变量里是同样内容）。生成：
  `openssl rand -hex 16`。会话密钥按 salt 派生（§6.0），PSK 轮换归运维。
  仓库不内置任何默认 PSK。
  - `--key=` 会出现在 `ps` 的进程命令行里，本机任意用户可见，只适合单用户主机
    或手工排障。
  - `--key-file=` 只暴露路径，但文件必须对**服务进程用户**可读。手工前台运行
    （以 root 或自己的账号）没问题；**deb 包内的 unit 用 `DynamicUser=yes`**，
    每次启动分配一个新的无特权 UID，读不了 root:root 0600 的 `/etc/fcp/psk`
    （`/etc/fcp` 本身也是 0750 root:root，连打开目录都会 EACCES）。
  - **装 deb 后用 `--key-env=FCP_PSK`**：`/etc/fcp/fcp.env` 由 systemd 以
    root 读取后注入服务环境，而进程环境只有服务用户和 root 可读，也不会出现在
    `ps` 里。仓库内的 conffile 已按这一方式给出推荐配置。
  桌面 GUI 的 PSK 由用户在表单里填入，必须与服务端一致；勾选“记住设置”时它存在
  WebView 的 localStorage，不勾选则不落盘。会话 salt 由程序每连接随机生成，
  GUI 不提供配置项。
- **UDP 端口**：默认 4460。**部署前实测云商防火墙**——部分云商只放行特定 UDP 端口
  （#22 实测：UDP/40001 报文到网卡但不进 socket，最终只能用 UDP/40000）。端口试探：
  服务端起在候选端口 → 本地 `ss -uln` 确认监听 → 客户端小流量实测。
- **PMTU**：`--mtu`（默认 1400）必须 ≤ 路径最小 MTU，否则触发黑洞故障模式
  （握手可过、data/parity 全丢、表现为吞吐骤降；§14.12）。不给 `--mtu` 时，启动会读本机
  最大的非回环接口 MTU，只在它小于默认值时才下调（例如 1280 的隧道接口会得到 1280；
  接口 MTU 与 `--mtu` 同为 IP 包长，IP+UDP 头只在计算载荷时减去一次）；显式 `--mtu`
  优先，且该默认看不到路径中途的隧道，跨网部署仍应按实测填。

## 4. 服务端部署（Linux）

```bash
# 最小参数（--key-file 避免 PSK 出现在 ps 里；文件须对运行用户可读）
fcp-server --key-file=/etc/fcp/psk --bind=0.0.0.0 --port=40000
# 生产推荐（可观测）
fcp-server --key-file=/etc/fcp/psk --bind=0.0.0.0 --port=40000 \
  --log=verbose --trace=/var/log/fcp/srv --idle=300000
# deb 的 systemd unit（DynamicUser）无法读 root 的 0600 文件，改用环境变量：
#   FCP_PSK=HEX32 fcp-server --key-env=FCP_PSK --bind=0.0.0.0 --port=40000
# 旧写法仍然有效：--key=HEX32 / -v / --stats=10000
```

| 参数 | 说明 |
|---|---|
| `--key=HEX32` / `--key-file=FILE` / `--key-env=VAR` | 三者择一；`--key-file` 的 PSK 不进命令行，`--key-env` 是 DynamicUser 包装下的可用形式（见 §3） |
| `--bind/--port` | UDP 监听（默认 0.0.0.0:4460） |
| `--k=N` | 钉死 parity（-1 自适应；短连接密集用 `--k=2`，§14.16）。必须 ≤ `min(--p, --p-max)`，否则启动报错而不是静默夹取 |
| `--p-max=N` | 控制器 parity 上限 0..7（默认 4）。规范 §8 的 5..7 档必须显式抬高；`--k` 的可用上界也受它约束 |
| `--fec-budget=R` | 冗余字节比上限（默认 0.50，0 = 不限；深队列/按流量计费链路收紧） |
| `--fec=D:P` | 集合几何（默认 `10:3`；两端一致才生效，协商取小）；`--d/--p` 仍可用 |
| `--max-sessions=N` | 并发会话上限（默认 256）。启动时按 fd 上限与地址空间估算，超限只告警不拒绝 |
| `--idle=ms` | 会话静默拆除（默认 300000；**应用响应慢于该值会被误拆**，见 §7） |
| `--dial-timeout=ms` / `--connect-timeout=ms` | 前者约束整个拨号（解析 + 全部连接尝试，默认 5000），后者是其中单个地址的 TCP 预算（默认 5000） |
| `--log=LEVEL` | `off`（仅退出时 stats）/ `stats[:ms]` / `verbose`；`-v` 是 `verbose` 的别名，`--stats=ms` 仍可用 |
| `--version` | 打印发布版本后退出（不要求 PSK；装完自检/排障用） |
| `--trace=PREFIX` | 每会话控制器轨迹 `<PREFIX>.<cid>.jsonl`（目录自动创建；#35 起 GUI 同款） |

守护化：`systemd`（`Restart=on-failure`）或
`setsid nohup ... >/var/log/fcp/server.log 2>&1 </dev/null &`（注意：远端 shell 里
`pkill -f` 会匹配命令行自身，用 `pkill -x fcp-server`）。

## 5. 客户端

### 5.1 CLI

```bash
fcp-client --key=HEX32 --host=<服务器IP> --port=40000 --local-port=1080
# 验收
curl --socks5-hostname 127.0.0.1:1080 http://<目标>/
curl --socks5-hostname 127.0.0.1:1080 https://<目标>/   # CONNECT + TLS，证书端到端校验
```

客户端专属：`--host/--port/--listen/--local-port`；其余与服务端同名同义
（`--k/--p-max/--fec-budget/--trace/--idle/--fec/--mtu/--window/--no-prewarm`）。

窗口参数（2026-11-02 合并为两个，旧拼写仍是别名）：

| 参数 | 作用 | 备注 |
|---|---|---|
| `--window=START[:MAX]` | START = 固定模式下的发送窗口；自适应模式下是**起点**，同时是**丢包项的地板**。MAX（可选）= 自适应上限，合法区间 **64..4096 KiB**（默认 1024） | 自适应下 START 不得低于引擎地板 64 KiB，也不得高于 MAX（旧代码会静默夹住并打一行 note，现在直接报错）。不给 START 时用上一条到同一对端会话收敛到的窗口作为起点（prewarm），显式 START 优先。自适应下纯丢包最多把窗口压回 START，再往下只有"自己造成的排队"这一条证据才行——高丢包链路上把窗口砍到 64KiB 会把隧道砍成饥饿（`M2代理设计.md` §7 第 1 条实测） |
| `--no-auto-window` | 回到固定 `--window`（对照测量用） | 此时给 MAX（`--window=START:MAX` 或 `--window-cap`）会报错而不是静默忽略 |
| `--window-cap=KiB` | 旧拼写，等价于 `--window=START:MAX` 的 MAX 部分 | 不能与 `--window=START:MAX` 同时出现；`--window=START --window-cap=MAX` 仍可用 |
| `--rcv-buf=KiB` | **只对固定模式有效**；不给时默认跟随 `--window`（不小于 256 KiB） | 自适应下接收上限恒为 MAX，此时给 `--rcv-buf` 直接报错。固定模式下不再需要手填：接收容量自动取 `max(窗口, 256 KiB)`，否则对端会被 256 KiB 的通告窗口卡住；内存受限时可显式调小 |
| `--auto-window` | 旧拼写，恒为默认值 | 只保留"不与 `--no-auto-window` 同用"的校验 |

内存口径：自适应默认（MAX 1024 KiB ⇒ 每连接 2 MiB）× `--max-sessions=256` ≈ **512 MiB 最坏
承诺**（按到达字节计，不是预留），是固定默认（256 KiB 窗口 + 256 KiB 缓冲 ⇒ 128 MiB）的四倍。
服务端要压内存就同时降 `--window` 的 MAX 与 `--max-sessions`；启动时若这个最坏值超过进程
地址空间或 fd 上限，会先打一行 warning（不拒绝启动）。自适应**不在线上协商**（与 §1.1 的
握手改版不同，混版不会握手失败）：新收端配旧发端只是白占内存，旧收端配新发端会把窗口静默
夹在它的接收缓冲，所以升级仍按 §1.1 的整体验证顺序走。

### 5.2 Tauri GUI

- 表单字段：服务器地址 / UDP 端口 / PSK（32 位 hex，可显示/隐藏） / 本地监听地址与
  端口 / MTU / **FEC 预算** / 钉 k；“记住设置”关时不落盘。
- GUI 没有窗口开关：自适应始终按引擎默认**开启**（起点 256 KiB、MAX 1 MiB），
  界面也不传窗口参数。所以 GUI 侧每连接最坏同样是 `2 × 1 MiB`；需要固定或
  自定义窗口请用 CLI（`--window` / `--window-cap`）。
- 没有脚本钩子：启动参数由表单生成，密钥经 `FCP_PSK` 环境变量传给 sidecar
  （不进 argv）。要脚本化部署请直接用 `fcp-client`（参数同名同义）。
- 分发：发布流水线把 `FCP.exe` + `fcp-client.exe` 打成单文件
  `FCP-<版本>-win64.exe`，双击即运行，无需安装（内部自解压到临时目录，
  退出后清理）。Linux 发布流水线产出 `FCP-<版本>-linux-x86_64.AppImage`：
  `chmod +x` 后双击，删除文件即卸载。两者都不写系统目录；配置保存在 WebView 的
  localStorage（勾选“记住设置”时）。

## 6. 观测与排障

### 6.1 stats 行（两端同格式）

```text
stats  220.2s live=0 up=42 tunnels=37 tx=6472895B rx=173696566B bad_entry=0 refused=5
       hs_failed=0 reset=0 idle=0 clash=0 over=0 unknown=0 tomb=50 duprec=0
```

| 字段 | 解读 |
|---|---|
| `live/up/tunnels` | 存活会话 / 已协商 / 已通隧道；**收尾应全部归零**（否则泄漏） |
| `refused` | 服务端拨号被拒（目标端口未开）——正常业务事件 |
| `hs_failed/clash/over` | 握手失败 / salt 冲突（第四方重放）/ 超会话上限 |
| `unknown` | 无主 salt 报文（应为 0；#29a 后死会话尾巴不再计入此项） |
| `tomb` | 墓碑吸收的死会话尾段重传（#29a；有值 = 对端尾巴被静默消化，正常） |
| `duprec` | FEC 先修复、重传后到（M4 触发器；持续 >0 才考虑延迟重传，见 M4_EVAL §1.1） |

### 6.2 控制器日志（需 `-v`）

```text
FECSTAT sets=219 expect=2189 rx=1976 rec=123 ... pre=97304ppm usable=41114ppm -> k=2 state=ON
FEC ledger: groups=200 fail=220000ppm k=2 peff=0.1369 (binomial 0.1380) kl=1.60 applied=2 skipped=0
FEC capped: parity/data=52.3% > budget=50.0% (k=5)      ← 触发字节预算
FEC ledger: ... skipped=N                               ← 账本被门拒（样本不足/主导 k 错位）
conn N ... closed: idle timeout [stream queued=... acked=... delivered=... rwnd=... rto=...]
```

- `pre`（修复前丢包）是策略输入；`usable`（FEC 没救回来的）决定 KCP/流层重传量。
- `peff > binomial` = 账本经验校正在上调（突发链路）；`kl` 是突发检测距离（≥1 nat 明显突发）。
- **销毁诊断行**：`acked < queued` = 发送方被确认卡死（看 rwnd/rto）；
  `delivered < acked` = 接收方应用不读——一眼定位停滞在哪一侧（#33③ 方法论）。

### 6.3 轨迹回放

```bash
fcp-replay --trace=srv.101.jsonl                 # 汇总：k 轨迹/CAPPED/峰值冗余比/agree
fcp-replay --trace=srv.101.jsonl --dump          # 逐报告轨迹（含录制对照）
fcp-replay --trace=srv.101.jsonl --budget=0.10   # what-if：候选参数重放
```

`agree=N/M` 是重放与录制的逐决策一致率——恒等（阈值标定的基线）。

### 6.4 吞吐标定（`fcp-bench`）

```bash
fcp-bench server --port=47123 --key=HEX32 [--mbps=M] [--seg=N] [--k=K]
fcp-bench client --host=<服务端IP> --port=47123 --key=HEX32 ...
```

两端 PSK 必须一致，且**必须显式给 `--key`**：工具没有内置测试键，缺省直接拒绝启动
（A2/P2' N7）。`--k` 不得超过几何常量 `P`（工具内置 `D=10,P=3`），否则在建立套接字前
就报错，不会先等完会合再失败。客户端每轮生成随机 salt 并经会合包交给服务端，
**新旧版本会合格式不同，不能混跑**。RESULT 的吞吐只计 `send()` 成功的报文，失败单独
计入 `tx_fail`（对抗审查 A2/A20）。

## 7. 已知部署坑（全部实测过）

1. **云商 UDP 端口白名单**：报文"到网卡不进 socket"= 防火墙没放行该 UDP 端口；换端口实测。
2. **hairpin 拨号**：服务端代理目标是"自己的公网 IP"时走出云防火墙再回来——小流量可用，
   大流量稳定性未保证；服务端目标尽量写内网/回环地址。
3. **idle 拆除 vs 慢响应应用**：会话静默 `--idle` 毫秒后拆除，正在等慢应用响应的隧道会被
   误拆（curl exit 52 empty reply）。应用响应可能慢时放大 `--idle`；FCP 层有数据在飞不算静默。
4. **小内存云主机**：2 核/2GB 实测 10 并发 8MiB 下载可触发重启；`--max-sessions` 与
   并发规模按内存预算。
5. **短连接自适应盲区**：活不过 2~3 个报告周期的连接全程 k=0（或 pinned）——短连接密集
   部署用 `--k=2`（或预热 `--no-prewarm` 反向）。
6. **trace 前缀目录**：#35 起自动创建；旧版本会静默不录制——升级到当前版。

## 9. 排障实例：GUI 客户端 UDP 静默失败（2026-10-31，开发机实录）

**现象**：GUI 代理页正常启动（SOCKS 监听、状态灯 OK），但任何隧道都无法建立；
`QUdpSocket::writeDatagram` 返回成功，对端服务端 **零收**（`-v` + stats 确认）。

**定位链**（可复用的方法论）：
1. 服务端 `-v --stats` 确认零收 → 排除服务端；
2. CLI 客户端同机同参数正常 → 排除网络/服务端/引擎；
3. python 复刻 GUI 的 socket 形态（0.0.0.0 绑定 + 同尺寸 UDP）正常到达 → 排除 OS 路径；
4. 引擎 `ProxyHost::start`/`onServerReady` 加 fprintf 探针 → Options 全部正确到达引擎；
5. **#23 时代代码现编现跑同样失败** → 排除代码回归，锁定"按二进制"的进程级拦截。

**根因**：本机安全软件对**首见二进制**（当日新编译、无签名）的 UDP 出站按哈希拦截——
同一机器上"今天早些见过的进程"全部畅通，新编译的 GUI（含旧代码现编版）全灭。

**处置**：安全软件中放行客户端二进制（当时是 Qt 的 `fcp_client.exe`；当前对应
`FCP.exe` 与 sidecar `fcp-client.exe`），或对构建输出目录建立信任；CLI 不受影响
（其二进制在拦截生效前已通过首次判定）。Linux 部署无此问题（无同款安全层）。

**引擎侧加固（已常驻）**：`ProxyHost::start`/`onServerReady`/`wireSend` 曾加临时探针
定位后移除；引擎销毁诊断（closed 行携带 stream 统计）保留为永久能力。

## 10. 排障实例：自适应窗口把隧道砍到地板（2026-10-31，境外 VPS 实测）

**现象**：代理默认开着窗口自适应，单流 32 MiB 反而比固定 256 KiB 慢 2.5 倍（1.61 vs 4.0 Mbps），
收尾诊断 `cwnd=65536` —— 窗口停在引擎地板一整轮。

**怎么读这行诊断**（`-v` 打开，隧道关闭时打印；现在只要窗口真的动过就会打印，干净收尾也有）：

```
conn 1 127.0.0.1:8099 closed: flushed and closed [stream queued=… acked=… delivered=…
unacked=0 in_flight=0 rwnd=1048576 cwnd=65536 rto=432 loss_rto=10 loss_dup=11106]
```

- `cwnd` 收尾值对比 `--window`：等于内置地板（64 KiB）而不是起点，就是被砍穿了。
- `loss_rto` / `loss_dup` 是**缩窗证据的归因**：前者是超时补发（真的什么都没回来），后者是
  dup-ACK 第二轮判定（对端卡在洞后）。本例 10 对 11106 —— 砍窗几乎全是 dup-ACK 造成的。
- 配合服务端 `FECSTAT`：`pre` 是线上原始丢包，`usable` 是 FEC 补完仍剩下的残留。这条链路
  `pre` 14.5–20% / `usable` 2–8%，`kl≈0`（不是突发）——"补包的包又被随机丢包吃掉"在这种
  链路上是常态，不是拥塞。

**根因**：控制律把流级丢包当纯拥塞信号，每个 epoch 判定丢包就 ×0.7，五个 epoch 落到地板；
地板之下几乎不可能出现"干净且窗口顶满"的 epoch，所以长不回来。

**处置**：丢包项的地板改为本流的起始窗口（`--window`），只有排队证据才允许更低（见
`M2代理设计.md` §2.1 与 §7 第 1 条）。运维侧不需要改参数，默认值即生效。

**仍然要认的账**：这条链路上自适应与固定 256 KiB 统计上不可区分——窗口不是受限项，FEC/ARQ
的放大才是（1 MiB 窗口那轮线上 83.5 MB 换 33.5 MB 净荷）。看到"自适应没提速"先量 `pre`：
原始丢包超过个位数百分点时，先修链路或调 FEC，别调窗口。

**同一轮里另外两条容易误读的症状**（都不是自适应的问题）：

- `the peer stopped acknowledging` 不必然等于传输停摆。若诊断里 `queued == acked` 且
  `delivered` 等于全文长度、只有 `unacked=1 in_flight=1`，那是**关闭段的最后一条没被 ACK**——
  数据已经交付完，判死发生在收尾握手。真停摆的形状是 `acked < queued`（发送侧卡在洞上）或
  `delivered < acked`（接收侧不再交付）。
- 本机同时活着两个客户端时，1080 上会有**两个监听者**（Windows 允许同址重绑），新连接被随机
  分到哪一个是不确定的。分到错 PSK 的那个，症状是 `curl` 直接 `code=000` 或只收到几 KB，
  同时在远端刷 `conn N closed: unauthenticated first datagram`——看着像握手回归，其实只是
  进程没清干净。脚本里的 `kill` 只杀掉包装它的 bash 作业、杀不掉 `.exe`，收尾要按图像名杀
  并确认 1080 只有一个持有者（`交付历史.md` §20.3）。
