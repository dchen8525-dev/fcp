## 2. 成立的发现

### F-1（Medium）握手信封的发送计数器起点只有 2³²，且 CSPRNG 失败时静默退化为 0

- **位置**：`src/fcp/session.cc:106`、`src/fcp/random.cc:48-52`、`src/fcp/envelope.h:102`
- **代码**：

```cpp
// session.cc:100-106（注释声明了意图）
  // ... A random 32-bit start makes every session's pair distinct ...
  hs_env_.set_send_nonce(random_u32());

// random.cc:48
uint32_t random_u32() {
  uint32_t value = 0;
  if (!random_bytes(&value, sizeof(value))) {
    return 0;          // 熵源不可用 → 起点恰好是 0
  }
  return value;
}
```

- **缺陷一（空间只有 32 位）**：`set_send_nonce` 收 `uint64_t`，这里只填 32 位。握手信封每会话
  只发个位数个包，按生日界，同一 `(PSK, salt)` 的起点在 **约 7.7 万个会话规模**上就会出现碰撞
  （√2³² ≈ 65536；重复抽样次数越多越接近必然）。碰撞意味着同一 `(key, IV)` 封出两条明文不同的
  ACK——正是 `#31` 要消除的密钥流重用前提。
- **缺陷二（失败静默）**：`random_bytes` 失败（容器无 `/dev/urandom`、FD 耗尽、`BCryptGenRandom`
  在受限沙箱失败）时返回 0，`set_send_nonce(0)` 是合法值，于是**所有会话的握手信封都从 IV 0 起**，
  精确回到 v6 的失败模式。`random.h` 自己的注释写着"需要非零值的调用方必须自己检查返回值"，
  这里正是那种调用方，却没有检查。
- **现有防线为何不覆盖**：`handshake_test` 的 `TestNonceIsRandom` 只覆盖 HELLO 载荷里的 nonce
  （那条路径失败会 `fail(kBadNonce)`，做法是正确的）；`envelope_test` 的 CSPRNG 用例
  只测 `random_bytes` 本身，不测这个调用点的返回值。
- **建议**（改代码时）：`random_bytes(&start, sizeof(uint64_t))` 填满 64 位；失败时让
  `Session` 构造失败并响亮报错，不要回退到 0。回归用例：注入一个必然失败的熵源，
  断言 `Session` 构造失败。

### F-2（Medium）用握手键封的非握手载荷被**静默丢弃**，与规格 §4.1 的两处承诺都不符

- **位置**：`src/fcp/session.cc:153-175`
- **规格原文**（`docs/协议规格.md:129-131`）：

> "此后再用旧键（含握手键）封的报文一律 `auth_fail`。"
> "成功后只放行 `type=oob` 且载荷为 HELLO/HELLO_ACK 的报文，其余计入 `struct_fail`。"

- **代码实际**：

```cpp
  if (bootstrap) {
    if (plain.size() < kFecHdrLen) { ++pre_struct_fail_; ... return true; }
    if (parse_hdr(...) && hdr_type(hdr.type_k) == SymbolType::kOob &&
        (is_hello(...) || is_hello_ack(...))) {
      on_oob(...);
    }
    sync_report_counters();
    return true;            // ← 其余情况：不计数、不报错、静默丢弃
  }
```

- **后果**：一个停在握手 epoch 的对端（或封包侧 bug）发来的数据包**既不涨 `auth_fail`，也不涨
  `struct_fail`**——恰好落在两个计数器之间。运维只能看到"对端没数据"，看不到"对端在用旧键"。
  这正是 `部署运维指南.md` §1.1 列出的第二类误混版本症状（"握手成功但 0 吞吐，`auth_fail` 持续增长"）
  所依赖的观测项；当前实现下该症状不会出现，排障会走偏。
- **安全影响**：不影响认证强度（包确实被丢弃），只影响**可观测性**与规格可信度。
- **建议**：非握手载荷走 bootstrap 键时计 `auth_fail`（或新增 `bootstrap_non_handshake` 计数），
  并同步规格措辞；`plain.size() < kFecHdrLen` 计的是 `pre_struct_fail_` 而规格写 `struct_fail`，
  两处措辞一起对齐。

### F-3（Medium）零窗口探测的发送侧没有独立速率上限，完全依赖对端 ACK 是否回来

- **位置**：`src/fcp/stream.cc:672-700`（探测触发）、`:186-200`（探测记账）
- **代码**：

```cpp
  // 探测触发的唯一条件是 in_flight_ == 0 且没有可发的空间
  if (in_flight_ == 0 && ... ) { last_probe_ms_ = now_ms; probe_credit_ = true; pump(now_ms); }
```

- **问题**：探测段发出后计入 `in_flight_`，直到对端 ACK 才清零；而零窗口场景下对端
  **不会推进 `cum`**（没有可接受的数据），它只会回同一个 `cum` 和 `rwnd=0`。于是：
  - 对端**回 ACK** → `handle_ack` 弹出该段（`cum` 覆盖它）→ `in_flight_ == 0` → 下一轮探测，
    间隔由 `probe_ms` 约束，行为正确；
  - 对端**不回 ACK**（ACK 丢失，或对端 host 卡死）→ `in_flight_ > 0` → 探测不再触发，
    只能等 RTO 重传该段。RTO 有 `rto_backoff_` 指数退避（上限 16×、5s），所以**不会形成风暴**。
- **结论**：速率上界实际由"ACK 或 RTO"提供，**不是无限放大**；但探测路径没有自己的预算，
  它的节流完全寄生在 ACK/RTO 机制的时序上。对端若稳定回 ACK 且 `probe_ms=500`，
  每连接每 2 秒 1 段（1360B）——可接受，但与"零窗口下发送方应近似静默"的直觉不同，
  且这段字节在 FEC 层仍会计入 wire 字节与 k 的观测输入。
- **建议**：给探测加一个"每 N 次探测强制指数间隔"的独立计数（与 RTO 解耦），或在 trace 里
  把探测段单独打标，避免它污染吞吐/冗余比统计。

### F-4（Low，性能）AES 密钥展开与 GHASH 的 H 每个数据报重算一遍

- **位置**：`src/fcp/gcm.cc:82-86`（`gcm_open`）、`:27-34`（`compute_tag`）
- **代码**：

```cpp
bool gcm_open(const uint8_t key[16], ...) {
  Aes128Key round_keys;
  aes128_expand_key(key, &round_keys);       // 每包一次密钥展开
  ...
  uint8_t h[16]; uint8_t zero[16] = {};
  aes128_encrypt_block(key, zero, h);        // 每包一次 E_K(0)
```

- **量化**：MTU 1400 的满包约 88 个 AES 块。每包额外多出**密钥展开（约 1 个块的等量工作）+ 1 个块
  的 `E_K(0)`**，约 **+2%** 的 AES 成本；不算大，但这是纯冗余——会话内 `send_key_` / `recv_key_`
  固定不变，`H` 与展开后的轮密钥完全可以缓存。
- **附带影响**：`gf128_mul` 的逐比特分支（已接受项 A12/R3-27 的定时侧信道）因此**每包**被调用，
  观测次数从"每会话几次"升到"每包一次"。A12 被接受的前提是"受控链路 + PSK 不泄露"，
  这个前提没变，但可观测样本量高了三个数量级；如果将来要收紧 A12，这里是第一个该动的地方。
- **建议**：`Envelope` 持有 `Aes128Key` 与 `H`，`install_keys()` 时算一次；`gcm_seal/open`
  增加一个接受预展开密钥的重载。线格式零改动。

### F-5（Low，可维护性）`StreamConfig::max_segment` 的契约由两个模块各写一半

- **位置**：`src/fcp/stream.h:66`（注释）、`src/fcp/stream.cc:179-189`（使用）、
  `src/fcp/frame_tx.cc:32-35`（拒收）
- **问题**：注释说 `max_segment` 是"会话能承载的最大段载荷"（应等于 `Session::mtu_limits().payload_max`），
  但 `Stream::pump` 不校验它，`FrameTx` 则在超限时**静默丢弃并计 `mtu_drops_`**。
  若 `limits_.valid == false` 时按 `payload_max == 0` 赋值，`pump` 的 `max_payload == 0`
  会让 `tx_pending_` 永不排空，而对端只会看到"没有数据"。
- **可达性**：当前引擎在 `attach_stream` 前先查 `config_valid()`，所以**不可达**；属结构性隐患。
- **建议**：`Stream` 构造时钳制 `max_segment`，或在 `pump` 里对 `max_payload == 0` 直接 `abort()`，
  让契约违反变成立即失败而不是静默黑洞。

| 检查项 | 结论 |
|---|---|
| 时钟单调性 | CLI `reactor.cc:97` 用 `steady_clock`；GUI `proxy_host.cc` 全程 `QElapsedTimer`。**没有**用墙钟，系统时间跳变不影响定时器 |

|---|---|---|

| P2-3 | FECSTAT 前向界 2²⁰ 会在正常速率下误判 | 该界是**单份报告**的前向差，不是累计。60s 区间、D=10 时需 >1 Gbps 才可能触及；单线程引擎远达不到 |

## 7. 处置建议（按性价比排序）

1. **F-1**：改 4 行（64 位 + 失败即失败）。安全收益明确，成本最低。
2. **F-2**：加一个计数器并同步两处规格措辞。纯可观测性，零风险。
3. **F-4**：缓存 `H` 与轮密钥。约 2% AES 成本 + 缩小 A12 的观测面。
4. **F-3 / F-5 / F-6**：随下次动 `stream.cc` 一起做。

### 7.1 修复过程中新暴露的三处（已一并处理）

1. **`recv_limit_` 与 `send_limit_` 被当成同一件事**。第一版只给发送侧加预算、接收侧保留 2^32，
   结果 `session_test`/`proxy_engine_test` 里所有"窥视握手流量"的 reader 全部认证失败（对端起点
   超过 2^32）。改为 `counter_ceiling_`（收发共享的拒收线）+ `send_limit_`（本信封的预算）两字段。
2. **in-flight 门与上限重开之间的顺序**。把"窗口重开即复位退避"写在 `in_flight_ != 0` 之后，
   导致恢复后的下一次停摆仍按 16x 起步（`TestZeroWindowProbeBacksOff` 的复位断言抓到）。
   复位移到闸门之前。
3. **A1 的语义在 64 位起点下收窄**（已在 #34 记录）：只有密钥持有者才能伪造落在对端合法封包
   上界之上的包，`salt_clash` 实际只剩 NAT 重绑定。`proxy_engine_test` 的伪造包因此从
   `set_send_nonce(5000)` 改为 `seal_at(UINT64_MAX-1)`。这是 F-1 修复带来的**安全收益**而非退步：
   旧实现下 PSK 持有者在 5000 处即可冒充，现在必须预测对端 64 位落点。
