## 1. 发现与修复

| # | 严重 | 问题 | 触发输入 | 修复 |
|---|---|---|---|---|
| A-1 | Low | `rs::decode` 在 `k == 0` 时：有缺失就 `return false`（对），但**全部到齐时返回 true**——违反它自己声明的输出契约（成功时 `recovered` resize 到 n）；一个 `k=0` 集合会被报成"解码成功"。树内唯一调用方 `FrameRx::try_decode` 在入口就拒绝 `k == 0`，所以不可触发，属契约违背 | 直接调用 `decode(syms, n, 0, ...)` | 入口直接拒绝 `k == 0`；`rs_test` 的 fuzz 从 `k = 0` 起改为 `k = 1 +`，并补一条 `k == 0` 必须失败的断言 |
| A-2 | **High** | `Reactor::rotate_log_file` 的 `close()` 之前没有清账：成功轮转后 `log_bytes_` 仍是旧文件大小，**下一行日志立刻再次轮转**——每次轮转把一个空文件改名为 `.1`、删掉上一个 `.1`，日志文件永远在 32 MiB 前后被清空；失败分支则每行都尝试一次 rename。两种情况都在 stderr 上无感，排障时只剩 stderr | `--log-file` 累计超过 32 MiB 后继续运行 | `close()` 之后统一重开并把 `log_bytes_` 归零，成功/失败都不会连续轮转；失败只打一次降级 warn，重试间隔为再写满 32 MiB |
| A-3 | Low | `Envelope::install_keys` 直接往正在使用的 `send_key_`/`recv_key_` 上重新展开密钥，`derive_direction_keys` 写下的两份方向密钥也没抹除，一直留在栈上 | 构造与 `rekey()` 每次调用 | 两个方向先展开到局部 `GcmKey` 再整体提交；`key_c2s`/`key_s2c` 与局部副本用完即 `secure_zero` |
| A-4 | Low | `FcpSettle` 的 `accounted_through_` 用 `0` 当"尚未计入"哨兵，但 **set id 0 是合法 id**（`FrameTx::set_id_` 从 0 起）：第一个集合就是 id 0 时，key 一直是 0，之后任何集合计入都会把 key 直接**跳到那个 id**，跳过中间未计入的集合，发送端的 R(k) 账本因此少算 loss | 会话头几个集合 | 新增 `have_accounted_` 标志，key 的语义回到"已计入的最低 set id（连续水位）" |
| A-5 | Low | 桌面端 `writeSelftestResult` 往临时目录的**固定文件名**写自检结果：Linux 的 `/tmp` 是 1777 共享目录，别人预置的符号链接会让 GUI 把 JSON 写进他指定的文件（例如截断用户的 rc 文件） | 本地攻击者预置 `/tmp/fcp-speedtest.txt` 链接 | 先 `remove()` 再用 `QIODevice::NewOnly`（`O_EXCL`）新建：链接与既有文件都进不来，最坏是自检报告缺失 |
| A-6 | Low | `MainWindow::loadSettings` 的 `remember_->setChecked()` 会发 `toggled` → `saveSettings()`；靠 `loading_` 挡住，但挡不挡得住取决于相邻两行的顺序 | 维护时把 `loading_ = true` 挪开 | `QSignalBlocker` 显式挡掉，注释说明"加载期间不得回写" |
| A-7 | Low | `restartTunnel` 可被同一轮事件重复触发（唤醒广播 `PBT_APMRESUMEAUTOMATIC` 与适配器轮询落在同一 event loop）：两次 `onStart` 排队，第二次撞上"代理已在运行"，界面上一条红字压在一条本来正常的隧道上；另外该路径的 3s 限频在"重建已排队"期间**不生效**（它读的 `tunnel_started_ms_` 要等 `onStart` 才更新） | 睡眠唤醒 + 网卡变化同时发生 | 新增 `restarting_` 门：重建排队期间第二次请求直接返回 |

| A-8 | Low | 本地入口被拒后（`closing = true`，phase 仍停在入口族）`parse_entry` 不看 `closing`：同一 socket 上后续字节仍被解析。实测这一路**不会**开出隧道（拒绝时未消费的帧头留在 `entry` 里，重解析把新请求也判成同一条非法请求），但会把 `bad_entry` 再计一次、并反复白解析一段没人再看的缓冲 | 同一连接依次写 greeting + BIND（被拒）+ 合法 CONNECT | `parse_entry` 循环与 `on_local_bytes` 都拒绝 `closing`；`proxy_engine_test` 补用例（旧代码上用例失败：`bad_entry` 变成 2） |
| A-9 | Medium | `ProxyEngine::on_wire` 先把报文交给 `Session::on_wire`（解密 → FrameRx → `host_.app_send`），**之后**才做源地址绑定判定：来自另一地址、认证通过的报文已经被完整处理（载荷进了应用、符号进 FrameRx、KCP sn 进了跨集去重表），日志却写着 "dropped"。NAT 重绑后上行能到应用、下行仍发往旧地址，隧道半活；更糟的是一个"已认证但原地址从未收到"的报文会把该 sn 记成已见，真正的副本随后被当重复丢掉 | 持 PSK（或路上截获一个原地址未收到的报文）从第二地址发一个新鲜报文 | 地址判定前移到 `Session::on_wire` 之前：地址不符的报文连一次 AEAD 都不做，不消耗 nonce、不碰 FrameRx；`salt_clash` 语义相应变为"同盐不同源"，日志去掉 "authenticated"。`proxy_engine_test::salt_routing_and_replay_binding` 改为断言两次地址不符都计数（旧代码上两处断言都失败：实际 0/1，期望 1/2） |
| A-10 | Low | 桌面端 `--fcp-speedtest-selftest` 用 `QString::fromLocal8Bit` 解子进程 stdout/stderr。子进程以 `/utf-8` 编译、`@speedtest` 行本身是 JSON（UTF-8）：非 ASCII 的 `error` 文本被按系统代码页解码成乱码，GBK 双字节还可能吞掉后面的 ASCII（最坏让 JSON 解析失败、明明测完却报"测速没有完成"）。同一份子进程输出在 `sidecar.cpp` 里一直用 `fromUtf8` | 在中文 Windows 上让测速返回带中文的错误 | 两处改为 `QString::fromUtf8`，注释说明子进程输出/ JSON 的编码约定 |
| A-11 | Low | `Sidecar::stopProxy()` 先 `process->disconnect(this)` 再置 `proxy_stopping_ = true`：置位永远晚于唯一读它的 `onProxyFinished` 连接，所以"用户主动停止"和"进程自己退出"在 UI 上无法区分。进程已经退出、`finished` 事件还排在队列里时点"停止"，会弹出"代理异常退出 (code N)"并点红 | 服务端不可达 → sidecar 自行退出 → 用户在事件到达前点停止 | 进函数第一句就置位（`proxy_` 为空也置，覆盖"已结束未观察"窗口）；`startProxy` 已有的复位保持 |

## 2. 复核后不成立（免得重走）

| 候选 | 复核结论 |
|---|---|
| **`FrameRx` 中断后黑屏**（代理报 High）：stale 检查排在 A8 跳跃确认之前，断流 gap > 256 个 set 后接收端是否永久卡住 | **不成立**：`stale_` 检查只在 **anchor 已经越过**该 id 时触发（`anchor_ - set_id`），而 anchor 只在 A8 确认后才前进；`sets_` 按 t_first 老化，活跃集合数不超过 256 时**不会**出现"无法继续前进"的死锁。主审写了 `TestGapWiderThanWindowReanchors` 试图证伪，该用例在改动前后**都通过**，说明旧逻辑本身就能走通——保持原顺序（先挡远端跳跃，再由确认推动 anchor），用例与改动一并撤回 |
| `Stream` 的 RTO / SACK 补充扫描用 `!seg.sent` 就 `break`，会不会"卡在未发送段上、漏掉后面的已发送段" | **不成立**：`pump()` 严格按 `tx_` 顺序发送，未发送段永远是队列尾部（`ack_advance_cum` 只从队头 pop 已发送段），所以"已发送段在未发送段之后"这种排列不存在。dup-ACK burst 的 `!tx_.front().sent` 守卫同理成立。当轮为此写过的改动已全部撤回 |
| `proxy_engine` 的 `set_delivery_pending(app_in + stream_in)` 在缓冲区清空后不归零，会把 `delivery_pending_ >= rcv_cap_` 锁在真值上 | **不成立**：`on_tick` 对每个 Conn 每 tick 都走一次 `flush_app`，该值每 tick 重算；清空后下一个 tick 即归零 |
| 随机 salt 的反射放大（未认证即可让服务端新建会话 / 抢走 salt） | **已裁定且留档**：`B-01` 的反向设计（salt 冲突只丢包、不拆会话，见 `src/proxy/proxy_engine.cc` 冲突分支注释），会话数由 `--max-sessions` 封顶；不重复处置 |
| `gui` 日志窗 HTML 注入、sidecar 尾部行丢失、打包脚本与 workflow | 前几轮已复核不成立，本轮重扫无新增结论 |
| `recvmmsg` 没带 `MSG_TRUNC`，超过槽长的报文会被静默截断 | **不成立**：`recvmmsg` 返回的是拷贝进 iovec 的字节数（未带 `MSG_TRUNC`），所以 `len` 永远不会超过槽长，不存在越界读；槽长是 `64 × wire_cap`（比 UDP 单包上限大得多），单包与 GRO 聚合都不够把它填满，没有截断路径。截断即使发生也只会落在认证失败上 |
| 代理引擎回调重入（`host_.*` 同步调用会删 Conn / 重哈希表 / 释放 peer 槽） | 逐路径复核后**未见**悬垂引用：`reap()` 用 id 而非引用跨回调，擦除前重新 `find(id)`；`finish_conn` 之后调用方不再碰 Conn；peer 槽以 `refs` 计数、`peer_retired` 才释放；`bench` 的会话析构 flush 用的是发送时刻已死绑的地址。唯一可观测的副作用是 peer 槽在连接被 reap 的瞬间才归还，这是设计 |
| GUI 点"停止"后 `proxy_stopping_` 标志 | **成立（Low）**：`stopProxy()` 先断开 finished 信号再置 `proxy_stopping_ = true`，后者因此从来不起作用；进程已自行退出、`finished` 还排在事件队列里时点停止，会弹出"代理异常退出 (code N)"和红点。改为进函数即置位 |
| `bench.cc` 的 2048 字节接收缓冲在 `--mtu > 2048` 时截断报文 | **不成立**：bench 的数据符号载荷固定为 `kDataPayloadLen`（1200），线上长度约 1.24 KB，`--mtu` 只影响会话配置与 `config_valid()`，不会放大实际报文；bench 也不开 PMTUD，没有探测包。`--mtu` 太小时 `Session::start` 返回 `kBadConfig`，工具会报错退出 |
| `Sidecar::stopSpeedTest` 不 `emit speedStateChanged(false)`，界面会卡在"测速中" | **不成立**：该函数只有一个调用方 `Sidecar::shutdown()`（进程退出前），此时按钮已无意义；正常结束/超时/异常三条路径都在 `onSpeedFinished` / `finishSpeedWithError` 里发信号 |
| `fcp-replay` 的 `ratio_peak` 语义与 `fgets`+`pending` 对含 NUL 行的处理 | 不是缺陷：`ratio_peak` 是每个记录间隔的 parity/data 比（记录本身就是区间计数）；trace 是纯数字文本，NUL 只可能来自文件损坏，此时按截断行解析后被当成坏行跳过，`ReadLines` 已有 1 MiB 上限与 `ferror` 检查 |
